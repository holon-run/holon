# Holon：让 Agent 随事件行动，持续推进工作

**事件驱动的 Agent 工作台：接入你的系统，按事件与时间主动工作。**


## 1. 让系统事件和时间安排，成为 Agent 的工作入口

CI 失败后，Agent 开始调查；新日志到达后，Agent 整理问题；到了约定时间，Agent 检查待办和服务状态。配置好职责、工具与触发条件，这些工作就可以由系统直接发起，无需你逐次打开对话、复制材料、再发出指令。

**Holon 通过 webhook 和定时任务，把 Agent 接入已有系统与工作流程。**

| 工作从哪里来 | 如何触发 | Agent 可以做什么 |
| --- | --- | --- |
| **外部系统事件** | CI、日志系统、业务服务通过 webhook 投递事件或发送唤醒信号 | 调查失败、处理新问题，或继续原有工作 |
| **时间安排** | 一次性定时器或周期任务在约定时间触发 | 回查进度、执行巡检、整理阶段报告 |
| **人的委托与反馈** | 通过 Web、TUI 或 API 提交目标、补充判断 | 启动任务、调整范围、接回人工决定 |

这里的主动性来自事先配置的职责与触发条件：事件或时间信号带来一次行动机会，Agent 结合上下文判断下一步，在授权范围内执行，需要人决定时再交回。

### 为主动工作保留持续的现场

你可以让一个 Agent 长期负责代码审阅，让另一个维护文档，也可以在团队服务器上部署调查和测试 Agent，持续跟进共同的问题。

Holon 为这些 Agent 提供运行环境：每个 Agent 有自己的角色约定、技能和工作记录，使用所在机器上的项目、文件与工具。事件可以带来一项新工作，也可以让 Agent 回到尚未完成的工作；你通过浏览器或终端检查进度，并在需要时介入。

一项工作需要等待测试、外部反馈或人工决定时，Agent 可以记录进度与等待条件；条件满足后，回到对应的工作继续推进。后台服务与宿主机保持运行时，关闭交互界面不会结束后台工作。

**Agent 负责理解目标并执行；Holon 管理持续工作的现场。**

```text
CI / 日志 / 业务系统 ── webhook ──┐
一次性 / 周期任务 ───── 时间触发 ──┼─→ 有明确职责的 Agent
用户 ─────────────── Web / TUI ──┘             ↓
                                    读取事件与已有工作状态
                                               ↓
                                    开始新工作 / 恢复已有工作
                                               ↓
                                    执行与验证 → 交付或等待
```

### 你可以从这些工作开始

- **个人开发：** 让 reviewer 持续跟进 PR、新提交和 CI，遇到争议时请你决定。
- **跨项目交付：** 围绕一个功能，依次修改服务端、SDK 和应用，并组织各自的验证。
- **团队协作：** 让共享 Agent 接收故障线索、整理 Issue，继续跟进修复版本和人工验收。
- **周期跟进：** 定时检查服务状态与待验收事项，发现变化后调查或更新报告。

Holon 适合有明确交付物、需要多个步骤、包含等待与交接的工作。它可以运行在个人电脑、远程开发机或团队服务器上；这里的“本地”，指项目和工具所在的宿主机。

## 2. Holon 提供什么

### 通过事件和时间主动工作

| 特性 | 具体功能 | 使用价值 |
| --- | --- | --- |
| **Webhook 外部触发** | 外部系统可向指定 Agent 投递事件内容，或发出唤醒信号供它回查状态 | 将 CI、日志和业务系统接入 Agent 的工作入口 |
| **定时与周期触发** | 支持延时触发与周期定时任务 | 按约定回查、巡检和汇总，无需每次人工发起 |
| **有状态的持续处理** | Agent 结合长期职责、工具和工作记录处理触发信号 | 新问题可以开始处理，已有问题可以继续跟进 |

Webhook 可以直接由 CI 中的 HTTP 请求调用；需要转换事件格式、筛选或路由时，可以通过适配器接入。收到事件后，Agent 仍需核对事实和当前工作状态，再决定采取什么行动。

### 角色与方法可以复用

| 特性 | 具体功能 | 使用价值 |
| --- | --- | --- |
| **长期存在的 Agent** | 独立的 AgentHome，保存角色约定、记忆与工作记录 | 与固定角色持续合作，积累工作依据 |
| **Agent Templates** | 用角色说明和技能引用初始化新 Agent；支持自定义和共享模板 | 把审阅、开发、文档或运维的工作约定复用到新 Agent |
| **按 Agent 管理 Skills** | 在技能库中管理可复用方法，分别为 Agent 启用或禁用技能；任务中按需读取 | 不同角色配置各自需要的工作方法，并可单独调整 |
| **模型选择** | 配置默认模型，并为特定 Agent 设置模型覆盖 | 按任务需要选择模型提供商与能力 |

模板定义角色的起点，Skills 提供可重复使用的方法，具体目标则由工作项承载。例如，审阅模板约定关注哪些风险，审阅技能说明如何检查 PR，而“跟进这次接口改动”是一项独立工作。

### 工作可以等待、恢复和验收

| 特性 | 具体功能 | 使用价值 |
| --- | --- | --- |
| **WorkItem 工作记录** | 保存目标、计划、待办、阻塞与完成报告 | 查看这件事做到哪里、为什么停下、怎样才算完成 |
| **显式等待与恢复** | 记录正在等待的命令结果、人工输入或外部条件 | 保留暂停原因，让后续触发与已有工作衔接 |
| **受监督的任务与子 Agent** | 跟踪状态、读取输出、补充输入、停止任务并接回结果 | 分派的工作有负责人、状态与结果归属 |
| **执行与交付可追溯** | 保留输入来源、工具执行记录和面向用户的完成报告 | 先阅读结论，需要时再核对执行依据 |

### 工作环境由你组织

| 特性 | 具体功能 | 使用价值 |
| --- | --- | --- |
| **多 Workspace** | 一个 Agent 可绑定多个工作区，并显式切换当前工作区 | 围绕同一个目标逐步处理多个仓库和目录 |
| **Git worktree** | 为编码任务创建独立工作目录 | 组织并行修改、方案实验和审阅环境 |
| **Web GUI 与 TUI** | 浏览器与终端连接同一个后台；另提供 CLI 和 HTTP 接口 | 按习惯选择入口，重新连接原有 Agent 与工作 |
| **自托管与一体化部署** | Rust 二进制内嵌 Web GUI，支持远程访问 | 可部署到自己的电脑或服务器，无需另外部署前端服务 |

这些能力组合起来，让“谁负责、在哪工作、怎样执行、何时继续、结果在哪”都有明确安排。

## 3. 场景一：一个持续负责审阅的 Agent

**适合：个人开发者，以及需要持续跟进代码质量的团队。**

先从审阅模板创建 reviewer，为它启用所需技能，并接入项目工作区和 GitHub / CI 事件。给它一项持续职责：

> 负责这个仓库的 PR 审阅。收到新 PR 后开始检查，重点关注兼容性和回归风险；新提交或 CI 结果到来后继续跟进。出现有争议的取舍时等我决定，为每个 PR 留下审阅结论和验证依据。

例如，CI 流程结束时向 reviewer 的 webhook 发送运行结果和 PR 线索。Agent 读取事件后核对状态：失败时调查原因并记录问题，通过时继续检查剩余条件。新 PR 可以带来新的工作项，已有 PR 的事件则用于继续对应工作。

| 阶段 | Agent 如何推进 | Holon 保留什么 |
| --- | --- | --- |
| 新 PR 事件到达 | 读取项目规则，建立工作项与检查计划 | 本次目标、范围与验收条件 |
| 执行审阅 | 阅读改动，运行检查，整理问题 | 执行状态、输出与进度 |
| 等待修改或 CI | 记录等待对象，让出当前执行 | 为什么等待、何时应当继续 |
| 收到新结果 | 核对新提交、测试结果与原有问题 | 同一项工作的连续记录 |
| 需要人工判断 | 说明争议，等你回复后继续 | 待决问题及后续处理 |
| 完成交付 | 汇总版本、问题处理与验证结果 | 可回看的完成报告 |

你可以关闭终端，稍后从浏览器连接回来。项目仍在原来的机器上，reviewer 的职责与未完成工作也仍然存在。

**这里体现的特点：CI 和 GitHub 事件可以直接发起 Agent 行动；固定角色持续接收工作，每项 PR 的进度又独立保留。**

*本例为工作流程示意。自动跟进 GitHub 变化需要操作工具、凭据和事件接入；也可以先由用户把新结果交给 Agent。发布或合并等操作应有相应授权。*

## 4. 场景二：围绕一个功能，协调多个项目与执行任务

**适合：涉及服务端、SDK、应用和文档的跨仓库变更。**

> 为这个接口增加一个字段，同步更新 SDK 和示例应用。分别验证兼容性；先整理方案，遇到影响旧版本的决定时等我确认。

开发 Agent 可以绑定服务端、SDK 和应用的工作区，围绕同一个目标逐步切换执行环境。每个项目的构建方式和指导文件仍留在对应目录；Agent 保留总体计划和各部分进度。

对于能独立推进的部分，可以把文档检查或独立复核交给子 Agent。需要并行修改同一仓库时，可以使用独立 worktree，分别保留改动和验证结果。

```text
一项功能目标：接口升级
          │
          ├─ 开发 Agent：服务端 → SDK → 示例应用
          │                    按步骤切换工作区
          │
          └─ 子 Agent：独立复核 / 文档检查
                               ↓
                    汇总改动与验证依据
                               ↓
                    用户决定是否接受交付
```

最终交付应回答：每个项目修改了什么、验证了什么、还有哪些兼容性问题，以及哪些环节需要人工确认。

**这里体现的特点：角色不绑定于单个仓库，工作目标可以跨工作区延续，独立执行的任务能够被监督和汇总。**

*本例为工作流程示意。一个 Agent 同一时刻只有一个当前工作区；多工作区用于组织和切换执行环境。worktree 用于组织独立改动，不能替代操作系统级安全隔离。*

## 5. 场景三：把共享 Agent 纳入团队分工

**适合：需要持续处理调查、审阅、部署和验收交接的团队。**

将 Holon 部署到团队服务器，让共享 Agent 承担长期职责。成员可以通过 Web 或 TUI 接入，也可以在配置好集成后，让 Agent 从团队原有的 Issue、PR、日志和发布事件接到工作，把结果交回共同使用的记录。

### 实践：从现场问题，跟进到修复后的验收

项目已有的[小团队实践记录](../website/zh-CN/blog/agents-in-a-small-team.md)描述了一个四人 AI 硬件团队：成员包括 Android、iOS 开发、产品兼市场负责人和测试人员。团队在服务器上部署 Holon，共享 Agent 持续承担调查、代码审阅、运维和验收跟进等职责。

其中两类交接体现了共享 Agent 的作用：

**现场材料到达后，调查 Agent 整理出开发可以接手的问题。**

设备日志上报触发 webhook，调查 Agent 读取获准访问的 trace，整理运行过程和定位线索，创建或补充 GitHub Issue。开发者接手时，可以直接查看原始场景、已发现的线索和待确认的问题。

**代码合并后，测试 Agent 继续跟进可测试版本。**

PR 合并可能已关闭 Issue，但修复还未部署或进入客户端安装包。测试 Agent 记录待验收工作，等待对应的部署或版本发布；版本可测后，核对实际包含的修复，形成验收清单。

可以通过请求与响应检查的部分，由 Agent 执行；需要在真机上确认的交互，由团队成员完成。已有人工结果可以直接核对和汇总，尚缺的结果则明确交给人复测，之后再更新验收记录。

```text
现场日志 / 问题反馈
        ↓
调查 Agent → GitHub Issue → 开发者修复 → 代码合并
                                            ↓
                              测试 Agent 保留待验收工作
                                            ↓
                              等待对应部署 / 版本可测
                                            ↓
                           自动检查 + 人工实测结果
                                            ↓
                              更新 Issue 与验收记录
```

团队共享的包括 Agent 的职责、项目环境和未完成工作。换一个成员接手时，可以继续使用已经积累的线索和记录；开发者也可以继续使用各自熟悉的编码工具。

**这里体现的特点：长期角色、事件接入和工作状态共同承接团队交接，工作在等待部署和人工反馈期间仍有明确归属。**

*本节根据仓库中的团队实践文章整理，并非本次重新运行或审计的结果。日志、GitHub 和部署系统需要相应接入；团队服务器的网络、凭据与访问范围由部署者配置。*

### 时间也可以发起工作

同样的工作方式也适用于没有即时事件的事项。例如，为测试 Agent 配置周期触发，检查仍未验收的修复，核对哪些已经进入可测试版本，更新清单并列出需要人工复测的项目。为运维 Agent 配置巡检周期，读取服务状态与近期异常，发现问题后展开调查并交付结果。

**事件触发让 Agent 响应变化，定时触发让 Agent 主动回查。两者都可以利用已有职责与工作记录，持续推进同一项工作。**

*以上定时流程是应用示例，未作为前述团队案例的已验证事实。*

## 6. 在自己的工作环境中开始

### 部署与接入

Holon 使用 Rust 实现，以二进制提供运行时和内嵌 Web GUI。使用发布构建时，无需额外执行前端构建或部署前端服务。你可以先在个人电脑上运行，再按需要放到远程开发机或团队服务器。

```bash
brew tap holon-run/tap && brew install holon
holon onboard
holon daemon start
holon tui
```

也可以从 [GitHub Releases](https://github.com/holon-run/holon/releases) 下载二进制。后台启动后，可以打开本地 [Web GUI](http://localhost:7878)，创建 Agent、管理技能与工作区、交代任务和查看进展。

### 选择一种起点

| 你想先尝试什么 | 第一步 |
| --- | --- |
| 一个长期合作的个人 Agent | 创建 Agent，配置角色与所需技能，接入一个项目 |
| 复用已有工作方法 | 安装或同步模板，再从模板创建 Agent；按需调整技能 |
| 让 Agent 随事件或时间行动 | 选择一项明确职责，接入一个 webhook 或配置一个定时任务 |
| 团队共享 Agent | 部署到团队服务器，配置远程访问，先选择一项边界清楚的共同职责 |

给第一个 Agent 的任务可以很小：

> 为这个项目里一个范围明确的问题建立工作项。说明计划与验收条件后执行，记录进度；需要我决定时暂停等待，完成后交付产物、验证结果和遗留事项。

### 使用前提

- **持续执行：** 运行所在的主机与后台服务需要保持可用。
- **工具与事件：** 模型、编译器、外部服务和事件接入按任务需要配置。
- **数据与权限：** 数据流向取决于模型和工具配置，本地执行使用宿主机权限。
- **结果验收：** 工作记录帮助跟进过程，完成质量仍需通过实际产物和验证结果判断。
