# Holon：创建和运行 AI 助手

**把具体工作交给助手，查看进展，持续跟进。**

Holon 是面向个人和团队的开源软件，让你在自己的电脑或服务器上创建和运行 AI 助手。你交代目标、材料和完成要求，助手使用配置好的工具处理工作，留下结果和依据。

从调查一个问题、审阅一项代码改动开始，也可以在接入工具和事件后，让助手持续负责来信分拣或异常跟进。需要等待回复或检查结果时，工作进度保留下来；条件满足后，接着处理。

**交出去一项工作**\
说清要解决什么、交付什么，以及哪些决定需要你确认。

**接得上已有进展**\
目标、发现和待办随工作保存，不必每次从头交代。

**需要时回来介入**\
查看结果和依据，补充信息、调整方向，处理需要你判断的问题。

![邮件、订单等系统变化、时间安排和人的输入进入 Holon；Agent 查看进度、判断下一步、执行检查并更新结果，需要条件时等待，条件满足后继续，达到要求后交付。](assets/work-loop-zh-CN.png)

## 把一项工作交给助手

不必先接入所有业务系统。选一项有明确材料和完成要求的工作，先验证助手能否交出有用的结果。

**1. 交代要求。** 提供目标、材料和验收条件。例如：“调查这份设备日志中的异常，交付复现线索、可能原因和待确认问题；不要修改代码。”

**2. 使用工具处理。** 助手在配置的工作环境中读取资料、运行检查、整理发现。需要修改文件或访问系统时，以配置的权限和你的授权为边界。

**3. 查看进展。** 先看结论、待办和等待原因，需要时再查看工具操作与原始依据，而不只是一段对话回复。

**4. 补充信息或作出决定。** 提供缺失材料、调整范围，或决定有争议的取舍。等待你回复时，已有发现和下一步保留下来。

**5. 验收交付。** 对照要求核对报告、文件或改动。检查未通过和仍未确认的部分应明确列出，而不是用“已完成”掩盖。

### 角色、方法和具体工作分开管理

Holon 中的助手称为 **Agent**，分别保存职责、记忆和工作记录。可以从模板创建，也可以按需要配置。

| 组成 | 用来说明什么 | 示例 |
| --- | --- | --- |
| **模板（Agent Template）** | 助手承担什么角色 | 问题调查、代码审阅 |
| **技能（Skills）** | 做这类工作时采用什么方法 | 日志分析步骤、审阅检查清单 |
| **工作项（WorkItem）** | 一件需要持续跟进的事的目标、计划和进展 | 跟进这次设备异常调查 |

工作区（Workspace）连接实际项目目录和资料。一个助手可以按任务切换多个工作区；编码任务还可以使用 Git worktree 创建独立代码目录。

## 工作为什么能持续推进

持续跟进不等于不停生成文字。Holon 记录工作正在等什么，并在相应结果或事件到来时恢复处理。

**等执行结果。** 检查命令或委派任务尚未完成时，先等待结果；完成后读取结果，再决定下一步。

**等人的判断。** 材料不足或需要批准时，把问题交回来。收到回复后，结合原有目标和发现继续，而不是重新开一件事。

**响应外部变化。** 通过 Webhook 接收系统消息，或提醒指定助手回查最新情况。例如，代码改动、检查结果或订单更新可以成为跟进信号。

**按约定时间检查。** 定时器支持一次提醒或周期检查，用于回查状态、整理摘要或跟进待办。

每件持续工作可以有独立的工作项，记录目标、计划、待办、等待原因和完成报告。新的消息和结果到来时，助手结合这些记录处理；完成后，读者可以先看报告，再核对来源与工具记录。

### 持续运行的前提

- **运行主机保持开启。** 关闭浏览器或断开终端不等于停止后台；关闭运行 Holon 的电脑或停止后台服务后，助手不能继续执行。
- **按需要配置接入。** 支持 Webhook 的系统可以发送通知；读取邮件、筛选内容或转换格式，需要相应工具或适配器。也可以先手动提供新结果。
- **通知不等于授权。** 系统消息与人的指令保留各自来源；接入事件并不自动授予发布、合并代码或访问其他系统的权限。

自行部署指 Holon 和工作环境运行在你选择的机器上，**不意味着模型推理全部在本地**。模型请求的数据流向取决于所选服务商和配置。

## 一个助手如何持续负责审阅

**适合：个人开发者，以及需要持续跟进代码质量的团队。**

从审阅模板创建助手，配置技能和项目工作区，再给它一项持续职责。可以先手动交给它一个 PR，之后再配置 GitHub 事件：

> 负责这个仓库的代码变更请求（PR）审阅。收到新 PR 后开始检查，重点关注兼容性和回归风险；有新修改或自动检查（CI）结果时继续跟进。有争议的取舍等我决定，为每个 PR 留下审阅结论和验证依据。

每次交付应说明：发现了什么问题、依据在哪里、哪些检查已执行，以及还有什么需要人决定。配置事件接入后，CI 检查结束可以通过 Webhook 通知助手；检查失败时调查原因，通过时核对是否还有未解决的问题。

![新 PR、新修改和自动检查结果依次触发审阅；等待期间保留问题和进度，同一个工作项记录审阅、复审与交付。](assets/pr-review-zh-CN.png)

**每个 PR 都有独立的工作记录。** 修改后的代码到来时，助手对照原有问题复核；等待修改或 CI 时留下待办，满足要求后交付报告。审阅结论不等于替人作出合并决定。

你可以关闭终端，稍后从浏览器回来查看。只要运行 Holon 的电脑或服务器及其后台服务保持运行，Agent 就能继续接收变化并跟进工作。

*本例为流程示意。自动接收 GitHub 变化需要配置工具、账号权限和事件接入，也可以先手动提供新结果。发布或合并代码需获得相应授权。*

## 个人使用与团队协作

个人使用时，可以让同一个助手持续负责项目，稍后回来接着查看。团队使用时，可以将 Holon 部署到服务器，让共享助手承担调查、审阅和验收等职责；成员通过网页或终端查看同一份进度，补充信息或接手处理。

[一个四人 AI 硬件团队的实践](../website/zh-CN/blog/agents-in-a-small-team.md)展示了两类交接：

**调查 Agent：把现场线索整理成可接手的问题。** 收到设备日志后，Agent 整理线索，写入问题记录（Issue），供开发者处理。

**测试 Agent：跟进修复是否真正可用。** 代码合并后，保留待验收事项；包含修复的版本可测试时，执行自动检查，汇总团队成员的实测结果。

![共享记录、Agent 和团队成员之间的交接：日志触发调查并形成问题记录，开发者修复后，测试 Agent 等待可测版本，结合自动检查与人工实测更新验收结果。](assets/team-handoff-zh-CN.png)

**团队可以随时查看谁在跟进、进展如何、下一步需要什么。** 换人接手时，已有线索和待办仍在；等待部署或人的反馈时保留进度，收到结果后继续。

还可以安排定期检查：哪些修复已经可以测试，哪些仍在等待，哪些需要团队成员补测。

*图示汇集实践记录中的两类交接，并非一次完整流程的实测；定期检查为配置示例。日志、GitHub 和发布系统需配置接入与访问权限。*

## 从第一项工作开始

先安装 Holon、配置模型服务并启动后台，再完成一项具体任务。确认结果有用后，再接入持续职责。

**1. 从模板创建。** 选择合适的 Agent 模板（Agent Template），复用角色设定和工作方法。

**2. 定义职责。** 写清负责什么、交付什么、什么时候需要你决定。选择所需技能，并明确它可以访问哪些资料和系统。

**3. 安排任务。** 给出目标、材料和完成要求。执行后，查看进度、补充信息，并处理需要你决定的问题。

**4. 再安排持续跟进。** 通过 Webhook 或适配器接收业务系统的消息，或设置定时检查；明确什么变化值得处理、什么时候需要你介入。

![Holon 中文网页工作台：选择 Agent，查看消息、进度、计划和等待原因，并补充信息。](assets/web-gui-review-zh-CN.png)

*工作台界面，内容为演示数据。左侧选择 Agent，中间查看消息与进展，右侧查看计划和等待原因；底部补充信息。也可通过终端界面接入同一个后台。*

### 选择访问方式

**网页与终端。** 安装包自带网页界面，也可通过 TUI 连接同一后台，回到已有助手和工作；自动化接入另有命令行与 HTTP API。

**手机连接。** iOS 与 Android 客户端连接运行中的 Holon，不是在手机上运行后台。远程访问需先配置连接与认证，测试版入口如下：

- [iOS · TestFlight](https://testflight.apple.com/join/XkTfN12S)
- [Android · 加入测试](https://groups.google.com/g/holon-pioneers/c/Cgs_KEAjdN0)：Google Group 测试说明，访问可能需要加入群组或取得权限。
- [Android APK 下载](https://github.com/holon-run/holon/releases)：在发布页选择 APK；直接安装需允许相应安装来源。

使用前配置模型、工具和工作区；持续跟进时，让运行主机和 Holon 后台保持运行。团队共享部署不等于助手之间已有强沙箱隔离，仍需明确资料、工具和访问权限。
