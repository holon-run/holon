# 为什么 Agent 的工作不应止于一次聊天

软件项目的工作方式，从来都不像一次聊天。

一个 Pull Request 要等待 CI；一次问题调查要等待日志；一次发布要等待批准；一个线上问题可能暂时没有新线索，直到新的反馈或事件到达才重新变得可行动。发起工作的人也可能已经合上电脑、切换项目，或者把下一步决定交给另一位成员。

但大多数 Agent 产品仍然从一个空白输入框开始，在对话停止时结束。它们很擅长在一次会话中回答问题、生成内容和执行任务。更难的问题是：**会话结束以后，那份责任还在哪里？**

对于真实项目，更有用的单位不是一段更长的对话，而是一项拥有明确生命周期、可以持续存在的工作。

## 聊天记录不等于工作状态

聊天记录可以保存“说过什么”，但不一定能清楚回答：

- Agent 最终要对什么结果负责；
- 哪些事实已经验证；
- 还有哪些步骤没有完成；
- 当前是真的被阻塞，还是只是在等待；
- 什么事件到达后，这项工作才应该恢复；
- 谁可以批准下一项不可逆操作；
- 工作属于哪个仓库、工具链和执行环境；
- 完成时应该向操作者交付什么。

更长的上下文窗口能让模型读到更多历史，但“读到历史”并不会自动产生可靠的工作生命周期。如果每次恢复都要靠“重新阅读整段聊天，然后猜测当前状态”，恢复本身就变成了一次重建。

用来回答一个问题，这可能足够；用来持续承担一项职责，就很脆弱。

## 真实工作里，大量时间本来就不该执行

很多工程流程等待的时间比执行的时间更长：

```text
检查 Issue
  → 准备或审查变更
  → 等待 CI
  → 检查结果
  → 等待部署
  → 验证行为
  → 等待人工批准
  → 交付或关闭
```

用轮询填满这些空档通常不是正确答案。它浪费资源、制造噪音，也没有说明“为什么现在需要再检查一次”。

更合适的运行时应该直接表达等待条件：

- 等待命令任务完成；
- 等待操作者做决定；
- 等待 CI、Pull Request 等外部对象发生变化；
- 等待定时器或计划中的复查时间。

没有可行动事项时，Agent 不需要持续“思考”。长期存在的是责任，暂停的是执行。

相关事件到达后，运行时应该恢复到对应的工作，而不是另开一段只有模糊通知的新聊天。

## 工作需要身份、状态，以及真正可以行动的地方

一个持续的 Agent 工作流，不能只依赖模型记忆。它至少需要四个组成部分。

### 1. 稳定的职责

Agent 应该拥有可识别的角色、运行规则和长期上下文。Reviewer、发布协调者或项目维护者，不应该每次打开终端时都从一段 Prompt 重新创建。

### 2. 显式的工作对象

在 Holon 中，**WorkItem** 表示一项可持续存在的目标。它可以保存计划、进度清单、就绪状态、等待条件和完成标准。锚定生命周期的是 WorkItem，而不是当前聊天窗口。

这让系统可以明确区分：

- 讨论与已经获准的执行；
- 可继续推进的工作与需要人工输入的工作；
- 正在运行的任务与对外部事件的等待；
- 暂时中断与真正完成的交付。

### 3. 真实工作区与工具链

项目 Agent 需要读取仓库、运行构建、创建隔离 worktree、调用已有工具并验证输出。工作区是执行契约的一部分：它决定指令作用在哪里，实际操作又发生在哪里。

只有持久状态、没有真实环境，得到的只是“对工作的持久描述”。Agent 仍然需要一个受控且真实的地方完成工作。

### 4. 清楚的交付边界

内部执行可能很长、很嘈杂；操作者通常只需要一个清楚的结果：改了什么、验证了什么、哪里失败、还需要做什么决定。

Holon 将内部执行过程与面向用户的 **brief** 分开。这样既能保留连续工作的证据，也不会让每一次工具调用都变成最终交付。

## 运行时不只要保存上下文，还要保存信任边界

一个事件唤醒了 Agent，并不表示这个事件自动拥有操作者权限。

Webhook、任务结果、公开 Issue 评论、系统 tick 和已认证的操作者输入都可能包含有用信息，但它们的来源和授权并不相同。持续 Agent 的运行时必须保存输入来自哪里、应该如何信任，以及它能够授权哪些动作。

Agent 承担工作的时间越长，这一点越重要。短暂会话可以依赖用户始终盯着每一步；长期工作流则必须在原操作者不在线时，依然清楚地维持权限边界。

如果没有信任边界，持久化只会让错误持续得更久。

## Holon 的方法

Holon 是一个开源、local-first 的持续 Agent 运行环境与工作台。在 TUI 和 Web GUI 之下，它以无头、事件驱动的方式运行。Holon 围绕一个简单目标构建：

> 让项目工作在对话结束后继续推进。

Holon 不试图把一次聊天无限延长，而是让工作拥有显式的运行时生命周期：

1. 一个长期 Agent 承担持续职责；
2. 一个 WorkItem 保存具体目标及其状态；
3. 任务在用户控制的真实工作区中执行；
4. 当进展依赖其他条件时，Agent 记录显式等待；
5. 任务结果、外部事件、定时器或操作者输入唤醒正确的工作；
6. Agent 从对应状态继续，最终交付简洁的 brief。

Holon 本身不是 Agent，也不是通用聊天界面。它是 Agent 周围的工作台：提供队列、任务生命周期、等待与唤醒、工作区绑定、来源、信任边界，以及长期工作所需的交付界面。

## 这意味着什么，又不意味着什么

长期运行不等于不受限制的自主执行，也不表示每个 Agent 都要持续占用资源，更不表示所有决定都应该交给 Agent。

好的持续工作流仍然需要明确的人类控制点。发布、合并、部署、花费资金、访问敏感数据或修改政策等动作，可能必须先获得批准。运行时应该帮助 Agent 带着相关证据到达决策点，然后等待，而不是悄悄跨过边界。

Holon 也仍然是一个早期项目。我们的目标不是用“AI 员工已经完成”的说法隐藏复杂性，而是让状态变化保持小、明确、可检查，并能在真实工具环境中发挥作用。

## 从一项天然需要等待的职责开始

评估持续 Agent 工作最简单的方法，不是先创造一个庞大的多 Agent 组织，而是选择一项本来就会跨会话、跨事件的职责：

- 跟踪一个 Pull Request，直到 CI 和 Review 都得到处理；
- 调查一个 Issue，并等待日志或复现证据；
- 协调一次需要人工批准的发布；
- 持续跟进一个要等外部条件变化的运维问题。

给这项工作一个清楚的完成条件。Agent 能行动时就行动，不能行动时就等待，正确事件到达时再恢复。

这就是“保存一段对话”和“保存一份责任”之间的区别。
