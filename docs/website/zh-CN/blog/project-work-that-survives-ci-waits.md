# 从 Issue 到发布：工作不会停在某个人的终端里

> **证据范围：** 本文描述一个经过匿名化处理的团队自托管研发实例。数字来自 **2026 年 9 月 7 日**采集的一次脱敏、只读快照，只能说明一个环境中的持续使用，不能作为性能基准、效率结论或同等效果承诺。实例描述和每一项数字在最终公开前，都需要操作者与实例团队逐项批准。

软件交付不是一个从头到尾连续执行的任务，而是一串被系统、人员和等待分开的责任：

- 一个 Issue 需要调查；
- 一个 Pull Request 需要审查；
- CI 需要时间完成；
- 部署之后还要验证；
- 发布可能需要明确批准；
- 新反馈也可能重新打开看似已经结束的问题。

如果这条链路的状态只存在于个人终端和临时 AI 会话中，团队就要反复重建同一组上下文：已经检查了什么？正在等什么？谁可以做决定？哪个结果到达后应该恢复工作？

一个小型研发团队正在用 Holon 验证另一种方式：把责任保存在团队控制的基础设施上，交给具名的长期 Agent 和显式 WorkItem，而不是留在个人聊天窗口里。

## 团队拥有的运行时，而不是一组个人聊天

该实例运行在团队控制的 Linux 主机上。通过 OIDC 认证的成员进入同一个 Holon 运行时。Agent Home、WorkItem、任务、等待和执行证据持续保存在主机中，同时连接团队已经在使用的仓库和工具链。

活跃 Agent 承担了相对稳定的职责，例如：

- Issue 与用户反馈调查；
- Pull Request 审查和合并条件跟踪；
- 修复验收与部署状态分类；
- 发布协调；
- 运行时与业务系统运维；
- 项目和产品协调。

关键不是 Agent 的数量，而是团队成员可以寻找一个稳定角色——reviewer、tester、release coordinator 或 ops——而不是寻找“上次处理这个问题的聊天窗口”。

## 一条交付链是什么样的

一个工程事项可能经过多个角色和外部系统：

```text
Issue、Pull Request 或外部反馈
  ↓
调查 Agent 核验问题并收集上下文
  ↓
Reviewer 检查变更与合并条件
  ↓
WorkItem 等待 CI、部署、反馈或人工决定
  ↓
Tester 区分代码、CI、部署和真机验证状态
  ↓
发布协调 Agent 准备下一项已获授权的交付动作
  ↓
Ops 继续观察服务或部署状态
```

没有一个 Agent 需要假装自己拥有整个流程。每个角色保留自己的职责与权限边界，连续性则来自显式工作状态和连接各阶段的事件。

CI 没有完成时，Reviewer 不应该无限轮询，也不应该宣布工作结束。WorkItem 会记录为什么暂时不能继续，以及什么条件应该将它唤醒。任务结果、外部事件或操作者输入到达后，运行时可以让 Agent 回到对应工作。

这是一个很小的状态变化，却改变了协作方式：等待不再是责任消失的地方。

## 一次持续使用快照

2026 年 9 月 7 日的快照在这个单一实例中记录了以下活动：

| 观察值 | 能够支持什么 | 不能证明什么 |
|---|---|---|
| 14 个活跃长期 public Agent | 团队使用稳定、具名的 Agent 角色 | Agent 越多，价值越大 |
| 5 个已启用 OIDC 用户，至少 4 个有输入记录的操作者身份 | 多个人实际使用共享运行时 | 人与人之间已经可以无摩擦接管 |
| 自 2026 年 6 月 26 日以来 1,663 个 WorkItem | 工作被保存在单次会话之外 | 每个 WorkItem 都产生了成功业务结果 |
| 1,627 个已完成、36 个开放 WorkItem | 生命周期被用于完成与持续跟进 | 相比旧流程已经产生可量化提升 |
| 10,667 次显式 `WaitFor` 调用 | 等待是主要工作状态，而不是边缘功能 | 每次等待都必要且配置正确 |
| 28,702 次外部 trigger 投递 | 大量工作由事件驱动 | trigger 数量等于生产力 |
| 23,081 个 Agent turn、187,875 次工具执行 | Agent 在真实流程和工具环境中反复行动 | 单独证明质量、节省时间或投资回报 |

快照时，14 个长期 Agent 中有 13 个处于休眠，只有 1 个处于唤醒或运行状态，但系统中仍有 29 个活跃等待条件。

这修正了“永远在线 Agent”这种容易误导的说法：持续存在的是责任，而不是持续繁忙的模型和进程。大多数 Agent 都在睡眠，直到某个事件让工作重新可行动。

## 工作跨越多个 Agent 角色的证据

对近期 WorkItem objective 的启发式检查识别出 234 个不同的 Issue 或 Pull Request 标识，其中 76 个曾由两个或更多 Agent 角色处理，约占这种识别方法找到标识的 32%。

常见组合包括 reviewer 与调查角色、reviewer 与 tester，也存在 reviewer、tester、调查或发布协调等多个角色形成的链路。

这不是严格的流程审计。标识来自 WorkItem 文本推断，可能包含分类误差。但它足以支持一个更窄的结论：这个实例并不是简单托管 14 个互不相关的聊天机器人；多个专业 Agent 正在同一工程对象的不同阶段周围工作。

## 人类仍然在哪里控制

该实例不会把“状态持久化”等同于“自动获得权限”。

Agent 可以检查状态、运行验证、准备变更、等待结果和汇总证据；不可逆或涉及政策的操作仍可以要求人类决定，例如：

- 批准发布；
- 在流程要求时批准合并；
- 接受安全或运维风险；
- 公开发布内容；
- 修改凭据、访问权限或生产策略。

长期运行时应该让这些边界更容易维持。Agent 可以带着证据到达决策点，等待有权限的操作者，而不是丢失工作或悄悄跨过边界。

## 这个实例证明了什么

现有证据支持四项结论。

### 会话不连续时，工作仍可以连续

持续 WorkItem、显式等待、外部 trigger 和反复的工具执行共同说明：这套工作流可以跨越事件和终端会话，真正有用的状态并不限于一段聊天记录。

### Agent 角色可以成为稳定的团队职责

团队已经把重复出现的工程责任交给具名 Agent。这些角色拥有不同工具、完成标准和等待条件。

### 真实环境是价值的一部分

Agent 围绕真实仓库、GitHub、CI、构建、部署和主机工具工作。它们的行动可以通过命令、任务结果、状态变化和 brief 检查，而不只是生成文字。

### 事件驱动的休眠比持续轮询更有用

快照中存在很多长期责任，但同时执行的 Agent 很少。运行时保存工作，在进展变得可能时唤醒相关 Agent。

## 它还没有证明什么

同一份证据也留下了重要问题。

### 还没有完整证明跨成员接管

多个人在使用实例，但快照无法可靠还原：成员 A 创建 WorkItem 后，成员 B 是否曾经只依赖记录状态、无需口头复述就完成理解和继续处理。这需要一次专门设计、可记录的实验。

### 使用量不是结果指标

WorkItem、turn、工具调用和 trigger 数量可以说明使用强度，但无法回答节省了多少时间、缺陷是否减少、发布是否变快。这些主张需要对照数据或经过确认的团队描述。

### 一个团队不代表普遍验证

这是一个工程团队使用的自托管实例。仍然需要第二个团队证明：在没有同样历史、基础设施知识和项目上下文的情况下，也能采用这套工作流。

### 长期状态有真实运维成本

快照时，Holon 数据目录约为 9.4 GB，主 SQLite 数据库约为 6.68 GB，Holon 进程常驻内存约为 2.24 GB。任务历史中同时存在完成、失败、取消和中断状态。

这些数字不是性能基准，而是在提醒：保留策略、日志轮转、备份、容量告警、失败分类和恢复能力，本身就是产品问题。长期工作会持续积累证据，而证据需要运维政策。

## 下一项验证

最有价值的下一项实验，是一次受控的跨成员接管：

1. 成员 A 创建一个真实 WorkItem；
2. Agent 工作，直到需要等待 CI、部署或人工决定；
3. 成员 A 不再继续参与；
4. 成员 B 只使用记录下来的 WorkItem 状态和证据；
5. 成员 B 响应等待或接管；
6. Agent 恢复到正确工作并产生可验证结果。

实验应该记录成员 B 理解状态需要多久、还需要问什么、是否必须由成员 A 重述上下文，以及 Agent 是否始终保持在权限边界内。

这比在面板上再增加一个 Agent 更重要。

## 到目前为止的结论

这个实例最重要的结果不是“一个团队运行了 14 个 Agent”，而是：

> 当 CI 仍在运行、部署尚未完成，或者原操作者已经离开终端时，工作仍然可以留在具名职责和显式 WorkItem 中，直到正确事件到达。

Holon 仍处于早期阶段，这也仍然只是一个实例。但持续工作已经不只是产品概念。它正在真实 Issue、Pull Request、工具、等待和团队角色之间运行，并暴露出长期 Agent 运行时下一步必须解决的问题。
