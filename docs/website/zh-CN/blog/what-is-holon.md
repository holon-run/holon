# Holon 是什么：为持续工作的 Agent 提供一个本地工作台

> 中文审阅稿，未发布。文中的审阅流程与首次体验任务用于说明使用方式；实际团队实践另有案例文章。

Holon 是供多个 Agent 持续工作的本地工作台。你可以在自己的电脑或远程服务器上运行它，配置负责开发、审阅、文档或运维的 Agent，让它们使用那台机器上的项目和工具，并通过终端或浏览器交代任务、查看进展、参与决定。

这些工作可以很短，也可能跨越几天：先完成一部分，等待测试结果或人的确认，再回来继续。Holon 保存 Agent 的身份和工作记录，用 Runtime 管理执行、等待与恢复。客户端是你连接这套工作环境的入口。

图中的 Runtime 运行在承载工作环境的机器上，Agent 在其中使用模型和工具推进工作，TUI 与 Web GUI 连接同一个后台。Mobile 仅表示未来构想，不是已经可用的独立客户端。

Holon 本身不是一个 Agent，也不提供一个新的基础模型。模型负责理解和判断，Agent 按职责执行；Holon 为这些 Agent 提供可以长期使用的工作环境。

## 已经有了 Agent 工具，为什么还需要 Holon？

一次代码修改结束后，工作未必结束。CI 可能还在排队，审阅意见要等开发者回应，修复后的版本还需要测试人员核对。如果这件事要继续推进，就得知道谁在负责、停在哪里、等什么，以及结果出来后该做什么。

Holon 选择把这些衔接纳入工作台本身：让有固定职责的 Agent 留在实际项目环境里，用明确的工作项记录进度，再按等待条件恢复执行。代码修改是其中一种任务，调查问题、整理文档和跟进验收也可以使用同一套机制。

远程开发是一个具体场景。开发环境在另一台电脑上，你希望多个 Agent 在那里工作，自己随时连接、查看结果或调整要求。关闭操作窗口后，项目和工作状态仍留在原来的机器上。

团队共享是另一个场景。成员各自使用 AI 工具之外，还可能需要共同的调查、审阅或测试 Agent。它们接收团队的工作，把结果写回大家已有的记录，需要人的判断时再交回来。

如果你需要有固定职责的 Agent 在真实项目里反复工作，并在等待和交接之后继续推进，Holon 提供了组织这些工作的环境。已有工具如果已经满足这些需求，就没有必要只为“常驻”或“多 Agent”再增加一套环境。

## 一个持续运行、可以随时连接的工作环境

使用 Holon 时，需要先分清工作运行在哪里，以及你从哪里操作它。

Runtime 的后台进程（daemon）管理 Agent 和工作状态。TUI 是终端入口，Web GUI 是浏览器入口；它们把你的要求送到后台，也让你查看 Agent 的回复、文件和工作进展。在 daemon 保持运行的前提下，关闭客户端不会停止后台工作。重新连接后，可以继续使用原来的 Agent，查看同一项工作的状态。

例如，你在开发机上交给 Agent 一项修改，开始运行项目测试后离开。测试命令由后台管理，Agent 可以等待结果，再检查失败原因或交付结论。你不必一直开着发出任务时的窗口；但如果下一步需要你确认，工作就应停在确认处，而不是自行扩大范围。

这里的“本地”以运行 Holon 的机器为准。它可以是手边的笔记本，也可以是远程开发机或团队服务器。项目文件、shell、工具链和工作记录围绕那台机器组织，客户端不需要携带整套开发环境。

部署在远程机器上时，网络连接、访问控制和凭据管理仍需妥善配置。常驻也不意味着不受故障影响：后台、模型和工具必须可用，保存了工作记录不等于任何中断都能无损恢复。

## 配置不同职责的 Agent，让合作可以积累

如果每次请 Agent 审阅代码，都要重新说明仓库约定、审阅标准和禁止合并的边界，合作就很难积累。Holon 允许你维护一个长期 reviewer，把这些要求作为它的职责保存下来，再不断交给它新的审阅工作。

### 职责、记忆和这一次的任务分开保存

每个 Agent 都有自己的 AgentHome，用来保存长期职责、记忆和自身材料，也是它默认的第一个工作区。`AGENTS.md` 可以说明它负责什么、可以自行执行哪些操作、哪些决定必须交给你。例如，reviewer 可以检查正确性、报告风险，但没有替操作者合并代码的授权。

“这个仓库希望审阅意见附上验证依据”可以成为长期约定；“这次检查哪个 PR、重点关注什么”则属于当前任务。稳定偏好、项目材料和临时进度分开维护，有助于后续执行时取用相关上下文，而不必每次把全部历史重新交代一遍。

记忆仍需要整理和修正。长期身份不会让模型拥有无限上下文，也不保证它能记住或正确理解每个细节。重要要求应写进明确的职责或工作记录，不能只依赖它曾经在聊天里读过。

### 用模板建立角色，用 Skills 复用方法

Agent 模板提供一个起点：初始化职责文件，并准备模板指定的 Skills。创建 reviewer 时，可以让它一开始就带有代码审阅的角色要求和流程；创建文档助手时，则选择与文档工作有关的方法。

Skills 是可复用的工作方法，可以包含操作步骤、检查要点和配套材料。它们可以按 Agent 启用。执行时先提供名称和用途，匹配任务后再读取具体内容，减少无关方法占用上下文。

模板用于建立 Agent，后续职责仍可以维护。给 Agent 启用审阅方法后，还需要另行配置所需的 GitHub 访问权限。配置入口见 [Agent 模板](/guides/agent-templates)与 [Skills](/guides/skills) 指南（英文）。

### 多 Agent 分工，需要明确交接

长期 Agent 适合承担反复出现的职责，例如开发、审阅或文档维护。一次工作中，也可以把有明确产出的子任务委托给子 Agent：主 Agent 修改代码，子 Agent 检查回归风险，主 Agent 接收结果后继续处理。

委托需要说明检查范围和预期产出。主 Agent 可以查看子任务状态、等待结果，但收到结果并不等于整项工作已经完成。发现的问题由谁修改、用什么检查验收，仍要在工作中安排好。

多个 Agent 的职责和上下文可以分别维护，但数量本身不会保证质量。是否拆分，应看这项工作是否需要单独的职责或检查过程。

## 让一项工作经过执行、等待，直到交付

一个 reviewer 可以长期存在，它今天审阅的 PR 则是一项有起点和结束条件的工作。Holon 用 WorkItem 保存这类需要跨轮次推进的目标，包括计划、进度、等待条件和完成报告。

下面以一次审阅为例，说明这些记录怎样参与执行。它是流程示例，不是一次实际审阅的复盘。

1. **接下目标。** 你要求检查一项变更，确认测试结果，并报告阻塞问题，不允许合并。Agent 记录目标和验收要求，开始读取变更与项目约定。
2. **执行检查。** Agent 分析代码，运行必要的本地检查。如果命令较长，可以把它交给受管理的后台任务，登记等待结果，再让出执行。
3. **等待反馈。** 本地检查结束后，可能还要等 CI 或开发者修改。工作项保留已发现的问题和下一步需要核对的内容，不因为这一轮没有动作就标记为完成。
4. **接回工作。** 等待条件满足后，Agent 重新核对实际状态：新提交是否解决了问题，检查是否通过，原来的意见是否仍然成立。计划改变时，更新同一项工作。
5. **交付结论。** 验收条件满足后，Agent 给出审阅结论、验证依据和剩余风险。若有必须由人决定的事项，就明确交回，而不是代替人作决定。

等待阶段不需要让模型反复询问“结果出来了吗”。Agent 登记具体条件，Holon 在相应唤醒到达后安排它继续处理。长命令结果、操作者输入和外部事件都可以参与这个过程。

不过，写下“等 CI”并不会自动订阅 GitHub。外部事件需要先配置接入；通知到达后，也要核对它对应的工作和实际状态。没有接入时，可以由你补充结果，再让 Agent 继续。

WorkItem 也不必用于每次聊天。解释一条命令、回答一个问题，可以直接结束；需要等待、后续交接或跨轮次推进时，才值得留下完整的工作记录。

最后的交付面向人，而不是一串工具日志。Holon 将完成报告与内部执行轨迹分开，方便你先看结论，再按需要追查依据。具体设计见 [WorkItem 如何接住一次中断](/zh-CN/blog/why-work-items)。

## 使用真实项目、工具和模型

Agent 的工作需要落到项目里。Holon 面向本地文件、仓库、shell 和已有工具链：修改文件后，可以运行项目自己的测试或构建命令；产出留在真实工作区中，供你检查、继续编辑或提交。

### 工作区让项目上下文有明确归属

一个 Agent 可以绑定多个工作区，同一时刻在一个工作区里工作。切换项目时，Agent 的身份保留，项目上下文和默认执行目录随之切换。一个 reviewer 因而可以服务多个仓库，而各仓库的代码和指导文件仍留在各自项目中。

对于编码任务，可以使用独立的 Git worktree，把不同修改放在不同工作目录里，减少文件改动互相干扰。代码仍要经过 diff 审查和项目检查，worktree 本身不会解决修改之间的逻辑冲突。

工作区组织执行上下文，不是文件访问的安全沙箱。尤其在本地 shell 可用时，应按实际的系统权限和工具能力管理风险。具体配置见[工作区指南](/guides/workspaces)（英文）。

### 按任务选择模型和工具

Agent 的职责与工作记录不必绑定某一家模型提供商。你可以在 Holon 支持的 Provider 中选择模型，保留已有的项目和工作组织方式。模型的工具能力、上下文限制和效果会有差异，更换后仍需用实际任务验证。支持范围见[模型参考](/reference/models)（英文）。

除了文字和代码，Holon 也提供图片理解与生成的工具入口。Agent 可以通过 `ViewImage` 读取界面截图，辅助检查布局；也可以通过 `GenerateImage` 为文档准备配图。这样，一项文档工作可以从正文延伸到配图和页面检查，但需要配置对应模型与凭据，并非所有对话模型都支持这些能力。详见[图片理解](/guides/view-image)与[图片生成](/guides/image-generation)指南（英文）。

“本地优先”描述的是工作环境和状态的组织方式，不代表模型推理必然离线。使用远程 Provider 时，请求仍会发往相应服务，项目材料的可发送范围需要由使用者决定。

## 从个人工作环境，到团队共享 Agent

个人使用时，可以围绕自己的项目建立几个长期角色。例如，开发 Agent 处理修改，reviewer 检查风险，文档 Agent 维护使用说明。你决定它们各自的职责、工作范围和验收要求，通过客户端在需要时介入。工作环境放在远程机器上时，这套分工也留在那里。

团队使用则多了一层交接要求：Agent 从哪里接收工作，分析结果写到哪里，遇到阻塞找谁，哪些部分必须由人完成。这些安排比先创建多少个 Agent 更重要。

在[小团队的 Agent Native 实践](/zh-CN/blog/agents-in-a-small-team)记录的案例中，团队已经把 Holon 部署到服务器，让共享 Agent 承担调查、审阅、运维和验收跟进。调查 Agent 根据日志和问题记录整理分析，结果进入 GitHub Issue；修复后的版本可测时，测试 Agent 继续核对，把需要真机操作的部分交给测试人员，再接回反馈。

开发者在这个案例中继续使用各自的编码工具，共享 Agent 负责团队共同的工作。个人也可以把 Holon 作为主要的远程 Agent 工作环境。两者是不同用法，不需要把“替换现有工具”或“只做后台补充”设成统一前提。

Holon 已用于这样的共享实践，但还不是完整的团队权限管理产品。部署者仍需安排访问控制、凭据和操作边界。

## 持续工作时，人的控制权放在哪里？

把工作交给 Agent 之前，应明确它可以做什么，以及哪些操作需要确认。例如，允许它读代码、运行测试和起草修改，不代表允许它发布文章、合并 PR 或部署生产环境。

Holon 区分操作者输入、外部事件和工具结果，保留来源与信任信息。一条 PR 评论可以提供新的线索，一段命令输出可以解释失败原因，但它们不能因此获得修改授权边界的权力。外部通知到达后，Agent 仍应按原有要求核对状态，决定下一步。

职责、Skills 和角色分工规定 Agent 应怎样工作，并不构成权限隔离；实际访问范围仍取决于系统权限、凭据和运行配置。对于影响较大的操作，可以把人工确认写进流程，让 Agent 在执行前等待，而不是做完后才报告。

## 先交给它一件边界清楚的事

第一次使用，不必先配置一整组 Agent 或接入外部事件。按[第一个 Agent](/zh-CN/getting-started/first-agent)完成安装与模型配置，在一个可写的练习工作区里给出这样的要求：

> 为这个项目起草一份贡献指南。先阅读现有文档，记录目标和计划，只提交提纲，等待我确认后再写正文。完成后运行已有文档检查，报告结果；不要提交 Git commit，也不要对外发布。

收到提纲后，可以先断开客户端，再重新连接，找到原来的工作并确认范围。接着检查正文是否真的写进项目，验证结果是否有依据，最终报告是否说明未完成的事项。

这个练习同时涉及文件操作、工作记录和人的介入，不需要预先搭建 GitHub 事件接入。确认这条流程符合你的使用习惯后，再尝试更长的审阅任务，或把一项团队职责交给共享 Agent。
