# Holon 是什么：为持续工作的 Agent 提供一个本地工作台

> 中文审阅稿，未发布。文中场景用于解释工作方式，不代表已验证的用户案例。

## 为什么做 Holon：工作经常跨越一次对话

设想一个常见的下午：Agent 已经改好代码，补了测试，CI 还在排队。你准备离开，留下一句“结果出来后再检查”。第二天回来，检查失败了，你需要弄清昨天做到哪一步、Agent 是否看过日志，以及下一步能直接修，还是要先作决定。

修改本身可能只花了十分钟，后面的等待却跨了一晚。类似的断点也出现在资料收集、文档审阅和发布准备中：一部分工作能立即完成，另一部分必须等命令、外部反馈或人的确认。

模型可以读代码、分析问题、调用工具，但步骤之间仍需要有人保存目标、记住等待对象、安排下一次执行，并判断什么时候才算交付。Holon 要做的，就是为 Agent 提供这层持续工作的基础。

## Holon 是什么：模型之外的工作环境

**Holon 是供 Agent 持续工作的本地工作台，底层是管理执行与工作状态的 Runtime。** Holon 本身不是一个 Agent，也不只是一个聊天界面。

模型负责理解和判断，Agent 按照自己的职责推进工作；Holon 为它们提供身份、工作区、工具和调度机制。你可以在其中维护一个负责代码审阅的 Agent，也可以配置负责文档或运行维护的 Agent。它们使用什么模型、操作哪个项目、哪些事情要先问你，都需要明确设置。

聊天仍然是交代任务的方便方式。区别在于，后续执行不必只依附在这段对话上：Agent 有长期身份，一项跨轮次的工作有独立记录，等待也有明确的恢复条件。

## 谁持续负责：有职责和记忆的 Agent

如果每次请 Agent 审阅代码，都要重新说明仓库约定、审阅标准和禁止合并的边界，合作就很难积累。

每个 Agent 都有自己的 AgentHome，它也是默认的第一个工作区，用来保存长期职责、记忆和自身材料。比如，一个 reviewer 的长期职责可以是“检查正确性、报告风险，不替操作者合并”，具体这次审哪一个 PR，则属于本次工作。

Agent 还可以绑定多个项目工作区（workspace），并在它们之间切换。身份不变，当前工作的文件、项目约定和默认执行目录随之切换；项目代码和项目指导仍留在各自的工作区里。这样，一个 reviewer 可以负责多个仓库，而不必为每个仓库重新建立身份。同一时刻只有一个活动工作区；这种上下文组织方式不是文件访问的安全沙箱。

记忆也不意味着把所有历史都塞给模型。稳定的偏好、长期职责和当前任务材料需要分开维护，执行时再组织相关上下文。更换窗口之后，身份和记录仍在；模型的上下文长度与判断能力并不会因此变成无限。

创建这样的 Agent，不必每次从空白开始。Agent 模板可以初始化 AgentHome 中的 `AGENTS.md` 职责文件，并按模板配置准备所需的 Skills，也就是可复用的工作方法。创建 reviewer 时带上审阅流程，创建运营 Agent 时带上内容与研究方法，省去重复配置。

Skills 多了以后，也不必把每种方法都交给每个 Agent。Holon 支持按 Agent 启用相关 Skills，执行时先提供名称、用途等目录信息，匹配任务后再读取具体方法，减少无关内容占用上下文。全局和项目级 Skills 仍可能参与其中，因此这是按职责组织能力，而非完全隔离。模板负责初始配置，工作区负责组织当前项目上下文，两者配合使用。

具体配置见[工作区](/guides/workspaces)、[Agent 模板](/guides/agent-templates)与 [Skills](/guides/skills) 指南（英文）。

当工作需要分工，可以设置多个长期 Agent，也可以把一个有明确产出的子任务委托给子 Agent。例如，主 Agent 修改代码，子 Agent 独立检查回归风险，再由主 Agent 汇总结果。委托具有可检查的执行状态和结果，而不只是几个角色轮流发言。职责拆分不等于权限隔离，也不能代替最终验收。

## 一项工作怎样继续：把进度和等待留下来

Agent 的身份回答“谁负责”，WorkItem 回答“这件事进行到哪里”。

对于需要跨轮次推进的目标，Holon 用 WorkItem 保存目标、计划、进度、等待条件和完成报告。计划变了，就更新同一项工作的记录；不能因为发出了一条命令，就把整项工作标记为完成。临时问一个问题则不必建工作项，直接回答即可。

以准备一篇产品文档为例，一项工作可能依次经历：整理提纲、写初稿、等待你确认范围、修改正文、运行文档检查、交付审阅稿。等你确认时，工作尚未结束，但也没有必要反复调用模型询问“可以继续了吗”。

Holon 的等待与唤醒机制让 Agent 登记具体条件，然后让出执行。长命令可以作为受管理的任务运行，结果返回后继续处理；需要人工决定时，停在等待操作者输入的位置。外部事件也能触发后续处理，但必须先配置事件接入，写下“等 CI”并不会自动订阅 GitHub。

这就是持续工作与持续运行模型的区别：该执行时执行，该等待时等待。后台、模型和工具仍须可用，持久记录也不保证任意故障后都能无损恢复。

等到验收条件满足，Agent 应交付一份人能直接使用的报告：改了什么、怎样验证、还有什么未完成。Holon 将这种面向操作者的交付与内部执行轨迹分开；查看进展不应要求你先读完全部工具日志。更具体的设计见 [WorkItem 如何接住一次中断](/zh-CN/blog/why-work-items)。

## 在哪里工作：真实工具链，同一个后台

Holon 面向实际的本地文件、仓库、shell 和开发工具链。Agent 可以在授权范围内读写文件、执行检查；编码任务也可以放进独立的 Git worktree，减少不同修改之间的干扰。验证使用的是项目自己的测试和构建命令，结果落在真实工作区里。

Agent 的职责和工作记录不必绑定某一家模型提供商。你可以在 Holon 支持的 Provider 中选择模型，而不必因为换模型就重新组织项目和工作记录。不同模型的工具能力与效果仍有差异，需要按任务验证；支持范围和配置入口见[模型参考](/reference/models)（英文）。

除了文字和代码任务，Holon 也内置了图片理解与生成的工具入口：Agent 可以用 `ViewImage` 读取界面截图，辅助检查布局问题；也可以用 `GenerateImage` 为文档生成配图。这些能力仍依赖可用的对应模型、Provider 配置和凭据，并非所有对话模型都支持。配置方法见[图片理解](/guides/view-image)与[图片生成](/guides/image-generation)指南（英文）。

TUI 和 Web GUI 是连接这个后台的操作入口。在 daemon 保持运行的前提下，关闭客户端不会停止后台工作；回来后可以继续查看同一套 Agent 和工作状态。图中的 Mobile 仅表示未来构想，不是已经可用的独立客户端。

“本地优先”指工作环境和状态围绕本地组织，不代表模型推理必然离线。使用远程 Provider 时，请求仍会发往相应服务；本地执行也不是安全沙箱，需要控制文件权限、凭据和工具的可操作范围。

## 怎样开始：先交给它一件边界清楚的事

持续执行需要保留人的控制权。Holon 区分操作者输入、外部事件和工具结果，保留来源与信任信息。一条 PR 评论或一段命令输出可以提供线索，却不能因此获得修改授权边界的权力。外部通知到达后，Agent 仍应检查实际状态，按原有要求决定下一步。

第一次可以按[第一个 Agent](/zh-CN/getting-started/first-agent)完成配置，在一个可写的练习工作区里给出这样的要求：

> 为这个项目起草一份贡献指南。先阅读现有文档，记录目标和计划，只提交提纲，等待我确认后再写正文。完成后运行已有文档检查，报告结果；不要提交 Git commit，也不要对外发布。

这个练习不需要外部事件接入，就能检查几个重要环节：Agent 是否留下明确的计划，是否真的停在等待确认的位置，断开客户端后能否找到原工作，以及最终报告是否对应实际文件和检查结果。

Holon 更适合反复跨越执行、等待和人工决定的工作。如果只是解释一条命令，普通的一次对话就足够。可以从一项小工作开始，确认它能在该停的时候停下、回来后接着做，再扩大职责范围。
