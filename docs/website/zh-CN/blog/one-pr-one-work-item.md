# 不止审一次代码：用 Holon 搭建持续跟进 PR 的 Reviewer

> **中文审阅稿 · 未发布。** 本文依据 2026 年 9 月 10 日采集的本机 `holon-reviewer` 与服务器 `tuptup-reviewer` 记录。Holon PR 案例已与 GitHub 数据交叉核验；服务器案例来自保存的工作计划，已隐去仓库、人员和业务细节，未独立复跑验证。下文状态摘要均为整理，不是原文引用。

作者推送了修复，reviewer 确认原来的问题已经解决。几分钟后，CI 又红了。

这次应该继续挡住 PR，还是把红灯归给另一个问题？上次的结论对应哪次提交？修复到底验证到了哪一步？一次审阅评论通常回答不了这些后续问题。

Holon 项目里的 PR #2854 就经历了这样的过程：第一次修复解决了调度回归，但带入了错误的测试期望；reviewer 再次提出阻塞意见，作者修正后，才等到最终检查通过并合并。这篇文章沿着这条真实 PR，看看一个长期 reviewer 怎样把审阅跟到底。

## 先有一个持续负责的角色

`holon-reviewer` 模板定义的工作包括代码审阅、PR 生命周期跟踪，以及授权范围内的合并判断。创建这个 Agent 后，可以不断交给它新 PR，不必每次重新说明职责和工作方法。

模板把几件事分开：`code-review` 负责问题与证据的判断，`github-review` 负责 GitHub 审阅流程，`ghx` 约束平台操作；AgentInbox 负责收取后续事件。模板的准备方式见[Agent 模板指南](../../guides/agent-templates.md)。工具可用、平台凭据可用和操作者授权，是三个需要分别确认的条件。

对于持续跟进，模板要求先确认能否订阅事件、发布批准、合并，以及代作者修代码。本文采集到的 reviewer 有执行合并的记录，不能因此把自动合并当成新建 Agent 的默认权限。

角色职责长期保留，具体 PR 则由 WorkItem 承接。**一条 PR 对应一个持续更新的工作项**：保存已审版本、阻塞项、验证结果和下一次等待条件。简单的一次性审阅不必照搬这套长期跟踪流程；需要跨提交、跨 CI 结果继续处理时，工作项才开始发挥作用。

## 一条 PR，三次提交，两次阻塞判断

PR #2854 修改了 WorkItem 的完成行为：Agent 完成另一项工作时，不应连带结束自己正在执行的工作。改动涉及当前执行与目标工作项的关系，光看函数是否返回成功还不够，需要验证后续调度是否正确。

以下时间均为 **2026 年 9 月 9 日，UTC**。提交和审阅时间来自 GitHub 快照，判断过程由 reviewer 的工作计划补充。

| 时间 | 发生了什么 | reviewer 如何更新判断 |
| --- | --- | --- |
| 10:54 | PR 创建，初始提交 `589405cc` | 检查完成语义与回归覆盖，随后等待 CI |
| 11:48 | 发布第一条阻塞审阅 | 两个 Scheduler E2E 场景失败，定位到同一轮创建并完成工作项时的分类错误 |
| 14:18 → 14:31 | 作者提交 `19f390ca`，reviewer 复查 | 确认修复了原来的绑定判断问题；继续等新提交的检查 |
| 15:08 | 发布第二条阻塞审阅 | 调度检查已通过，但 Rust 与 Coverage 暴露了一处被改反的测试期望 |
| 15:13 | 作者提交 `f7b93809` | 恢复该测试期望，等待这个最终版本的检查 |
| 15:51 | PR 合并，合并提交 `81619f9` | 随后记录合并证据并完成工作项 |

### 第一次：从失败现象追到触发条件

最初的代码审查记录没有发现阻塞问题。随后，两个调度端到端场景报出 `provider request failed: contract_error`。

这个错误表面上像模型请求失败。reviewer 的后续记录和公开审阅给出了更具体的解释：在一轮操作者输入触发的执行里，Agent 创建、选中并完成了工作项，但完成逻辑误把它当成与当前执行无关的目标，于是额外发起了下一轮请求；测试用的脚本化模型服务没有对应的下一步，便报错。

它没有把“CI 红了”作为全部结论，而是把失败场景、工作项分类和额外请求连起来，提出修复方向。此时工作项留下的状态可以整理为：

> 当前版本：`589405cc`。阻塞：同轮完成被误分类。证据：两个 Scheduler E2E 场景失败，已定位分类路径。下一步：等作者修复，再核对新版本。

### 第二次：旧问题解决，不代表这一轮结束

作者的 `19f390ca` 补上了当前有效工作项的判断。reviewer 复查后确认，原来的绑定问题已解决；新版本上的 Scheduler E2E 也通过了。

但该提交还改动了一条测试期望。Rust 与 Coverage 随后都在这条测试上失败。reviewer 对照前一版本、测试实际输出和完成契约，判断实现行为符合当前约定，改反的是测试期望，于是再次提出阻塞意见。

这一轮汇报需要同时保留两个结论：

> 已解决：原来的调度分类问题。仍阻塞：`tests/run_once.rs` 中的测试期望与当前完成契约不符。下一步：修正期望，在新 head 上重新检查。

如果只保留一个“审阅通过”的状态，第一次修复确认后就可能过早收尾；如果只保留“CI 失败”，维护者又无法知道原来的问题是否真的解决。

### 最后：把合并结果和工作收尾分开确认

`f7b93809` 恢复了测试期望。采集到的 GitHub 快照显示，最终 head 上 Rust、Coverage、Scheduler E2E Required 等检查成功；也有按条件跳过的任务，不能把它们写成“全部测试都执行通过”。

GitHub 记录的合并时间是 15:51:54。reviewer 在稍后的结果简报中记录了合并提交、两轮修复依据和工作项关闭情况，并注明 PR 专属订阅将随终态自动清理。本次采集没有读取订阅系统的清理结果，因此不把这句话当成清理已完成的独立证明。

从 PR 创建到合并接近五小时。这是包含作者修改、CI 和等待的墙钟时间，**不是 Agent 的工作时长，也不是节省时间的测量**。这个案例能说明的是：审阅判断跟着三个版本更新，第一次修复并没有让这项工作提前结束。

## 另一个 reviewer：修复成立，CI 仍可能是红的

服务器上的 `tuptup-reviewer` 留下了另一种情况。它的一份工作计划记录：作者已经自行合并了一项测试修复，PR 侧 CI 被取消，reviewer 接手时做的是事后审阅和主分支验证。

后续主分支 CI 仍然失败。reviewer 在计划中把同一个构建里的两段验证拆开：单元测试已经通过，原来的失败消失；接下来运行的资源 lint 失败，对应另一项已存在的问题。它还对照了修复前的运行，说明旧问题此前先挡住了构建，使后面的 lint 错误没有暴露出来。

记录中的处置是：向原问题补充修复证据，向既有 lint 问题补充当前阻塞状态，把关闭问题的决定留给负责人。它没有因为总状态是红色就否定本次修复，也没有因为 PR 已合并就停止检查。

这份计划也留下了一次判断更正：早先拿到的日志不完整，根因归属只是工作假设；后续记录拿到更明确的失败签名，补充了依据。保存工作状态的价值，也包括保留“当时还不知道什么”，避免把初步推断变成永久结论。

另一份涉及部署流程的计划，则记录了不同的权限边界：reviewer 完成审查，合并由操作者本人执行，随后再核对主分支检查。技术检查完成和获得合并授权，需要分别确认。

**这两段服务器案例是工作计划复盘。** 本轮没有独立查询对应仓库或重跑测试，不能据此证明代码没有其他问题。它们提示了持续审阅应该保存的判断维度：具体问题是否修复、当前验证还缺什么、剩余失败归谁，以及下一步由谁决定。

## 事件接进来，进度留在工作项里

前两篇已经解释了长期 Agent 和 WorkItem 的机制。落到 reviewer，有三个不同的职责：

- **GitHub 提供需要重新核对的事实。** 当前提交、审阅和检查结果都要按版本确认；一条通知只是变化线索。
- **AgentInbox 收取并保存事件，通知 Holon。** 它负责事件接入，不替 reviewer 判断合并条件。UXC 提供其适配所需的工具调用入口。
- **Holon 保存工作状态并安排后续执行。** reviewer 恢复时读取此前记录，再用新证据更新判断；需要等待时显式留下等待条件。

“收到通知”不等于“有一项新工作”。本机的另一条 PR 合并后，reviewer 又收到合并前 CI 的迟到通知。保存的简报将它识别为已处理结果的回声，没有因此重新开始审阅。

接入时，应按 PR 建立窄范围订阅并复用共享源，核对 CI 是否在覆盖范围内。重启后也要检查激活目标是否仍有效。需要兜底重查时明确记录期限；收件箱有事件，并不自动保证 Agent 已恢复或处理完毕。具体工作项操作见[WorkItem 指南](../../guides/work-items.md)。

## 从一条保守授权的 PR 开始

不必一开始就把仓库合并权交出去。可以先安装模板，检查代码读取、必要测试和事件工具是否可用，再给它一个明确的任务：

```text
请持续跟进 <PR 地址>，直到合并、关闭或我明确终止。
允许读取代码与检查结果、订阅该 PR 和 CI 事件、发布审阅评论。
本地验证范围为 <允许的测试与环境>。
不要批准、合并、推送修改、代作者修代码或访问生产环境。

为这条 PR 建立 WorkItem，记录已审 head、阻塞问题、验证和下一步。
新提交到达后，先复查旧问题，再检查新增差异；CI 必须对应当前 head。
代码问题、检查状态和人工授权分别报告。
达到合并条件后向我交接；等终态确认后清理任务订阅并完成工作项。
```

先验证一轮真实的“提交更新 → 收到事件 → 恢复复查”，再决定是否扩大授权。维护者需要看到的是一份能据此行动的结果：哪个版本审过了，问题为什么成立或已经解决，还缺什么证据，下一步应该交给谁。

## 数据范围与复用边界

本次采集保存了两类材料，原始业务细节不随文章发布：

| 来源 | 采集范围 | 不能据此推断什么 |
| --- | --- | --- |
| 本机 `holon-reviewer` | 最近 100 个工作项、300 条结果简报；主案例另保存完整计划与 GitHub PR 快照 | 不是全量历史，也没有人工基线，不能计算成功率、准确率或节省工时 |
| 服务器 `tuptup-reviewer` | 按修改时间取最近 100 份工作计划，其中 82 份非空 | 文件修改时间不是事件时间；计划不等于运行时状态，也不代表完整审阅历史 |

采集时间为 2026 年 9 月 10 日。本机主案例可按 `holon-run/holon` 的 PR #2854 及上述 SHA 核对；另一条本机 PR #2856 用于查看终态后的迟到通知。服务器材料通过 SSH 只读取得，未读取凭据或运行时数据库。两处采样口径不同，不能横向比较工作量。

本文面向希望把单次代码审阅扩展为持续跟进的维护者。先用一条低风险 PR 验证复查和交接，再扩大使用范围；这些记录还不足以支持无人值守合并的可靠性承诺。
