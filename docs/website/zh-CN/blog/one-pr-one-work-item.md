# 不止审一次代码：用 Holon 搭建持续跟进 PR 的 Reviewer

> **中文审阅稿 · 未发布。** 案例与统计来自 Holon 仓库自身的 `holon-reviewer`，数据采集于 2026 年 9 月 10 日。

作者推送了修复，reviewer 确认原来的问题已经解决。几分钟后，CI 又红了。

Holon 仓库的 PR #2854 就经历过这个过程。它修改了工作项的完成行为：Agent 完成另一项工作时，不应连带结束自己正在执行的工作。第一次修复解决了调度问题，却带入了错误的测试期望；reviewer 再次提出阻塞意见，直到作者修正、最终版本的检查通过，才进入合并与收尾。

| 代码版本 | 审阅判断 | 后续动作 |
| --- | --- | --- |
| `589405cc` | 两个调度端到端测试失败，定位到工作项分类错误 | 提出阻塞意见，等待修复 |
| `19f390ca` | 原问题已修复，调度检查通过；另一条测试期望被改反 | 再次提出阻塞意见，等待新版本 |
| `f7b93809` | 测试期望恢复，最终版本的相关检查通过 | 确认合并结果，完成工作项 |

这一过程发生在 2026 年 9 月 9 日，提交、公开审阅与合并结果已和 GitHub 快照核对。部分 CI 任务按条件跳过，表中的“通过”只指实际执行的相关检查。

下面从创建 reviewer 开始，让它接手一条 PR，并确认后续提交到达时，它能接着复查。

## 1. 从模板创建 Reviewer

先按[创建第一个 Agent](../getting-started/first-agent.md)完成 Holon 安装、模型配置，并启动常驻 runtime。运行 Holon 的机器需要能访问目标仓库，备好 GitHub CLI（`gh`）及项目测试工具。持续接收事件还会用到 AgentInbox 和 UXC，第 3 步会检查接入。

在自己的终端中，从官方模板创建一个名为 `reviewer` 的 Agent：

```bash
holon agent create reviewer --template https://github.com/holon-run/holon/tree/main/agent_templates/holon-reviewer
```

如果已经安装或同步了该模板，也可以用模板名；两种方式选一种即可：

```bash
holon agent create reviewer --template holon-reviewer
```

`reviewer` 是你创建的 Agent 名称，`holon-reviewer` 是模板名。若已有同名 Agent，换一个名称，不要覆盖原来的工作记录。

模板会为新 Agent 初始化 `AGENTS.md` 工作规范，并安装声明的 Skills。它已经包含持续审阅所需的方法：

- 审阅时给出问题、证据和验证范围，区分阻塞问题与普通建议。
- 为持续跟进的 PR 建立 WorkItem；新提交到达后复查旧问题，合并或关闭后收尾。
- 开始长期跟进前，确认订阅事件、批准、合并和代作者修代码的权限。

Skills 则提供具体流程：`code-review` 和 `github-review` 指导代码与 GitHub 审阅，`ghx`、`sview` 辅助平台操作和源码阅读，`agentinbox`、`uxc` 用于事件接入。你不需要从头写一套 reviewer 提示词。

创建后运行 `holon agent list`，确认新 Agent 出现在列表中，再从 TUI 或 Web GUI 选择它。模板结构和自定义方式见[Agent 模板指南](../../guides/agent-templates.md)。

## 2. 告诉它你的项目要求

通用工作方法已有模板负责，你主要补充这个项目的要求：仓库在哪、重点看什么、允许跑哪些测试、哪些决定要交给你。

例如，向刚创建的 reviewer 发送下面这段话，先替换其中的占位内容：

```text
你负责持续审阅 <owner/repo>，本地仓库在 <绝对路径>。
重点检查兼容性和回归测试，反馈使用中文。
允许读取代码、在独立 worktree 中运行 <测试命令>、
订阅目标 PR 与 CI 事件，并发布审阅评论。
不要批准、合并、推送修改、代作者修代码或访问生产环境。
达到合并条件时通知我，由我决定是否合并。

请把这些长期要求记入你的工作规范，检查仓库和工具是否可用。
缺少权限或环境时告诉我，不要自行扩大授权。
```

这里的“长期要求”属于 reviewer，后面交给它的新 PR 也沿用。某条 PR 特有的检查范围，再随那次任务补充。仓库本身的 `AGENTS.md` 仍然提供项目构建、测试和代码约定。

先看它的确认结果：是否找到了正确仓库、理解了测试范围、记住了禁止的操作。**模板附带的 Skill 是工作方法，不会自动提供 GitHub 凭据，也不会替你授予合并权限。** 仓库中的测试会执行代码，第一次试用应选自己熟悉的低风险 PR，并限制运行环境。

## 3. 让后续 PR 和 CI 事件能找到它

第一次审阅可以直接读取 GitHub；要在作者推送后继续跟进，还需要把事件接到这个 reviewer。

这套模板通过 AgentInbox 接收 PR 和 CI 变化，再通知 Holon 恢复工作；GitHub 适配会用到 UXC。若尚未安装或配置这些工具，可以让 reviewer 按它附带的 `agentinbox` Skill 检查，并按[AgentInbox 接入指南](https://agentinbox.holon.run/guides/onboarding-with-agent-skill)完成准备。

可以这样交代：

```text
请按 agentinbox Skill 检查持续跟进的接入条件：
AgentInbox 服务可用，GitHub 适配可读取目标仓库，
当前 reviewer 已登记为可接收唤醒的目标。
需要安装工具或导入凭据时，先说明所需操作，由我确认。
此时先不要订阅整个仓库；等我指定 PR 后只跟进该 PR 和它的 CI。
不要在回复里展示凭据或回调地址。
```

接入完成时，让它报告各项检查的结果和仍缺的条件。尤其要确认登记的是这个 reviewer，而不是另一个 Agent 或已经退出的会话。若之后迁移 runtime 或更换事件接收地址，也要重新核对。

具体到某条 PR，Skill 会指导它复用共享事件源，建立只覆盖目标 PR 的订阅，并包含 CI 更新。事件源和订阅准备好后，Holon 还需要留下相应的等待条件；只看到“订阅成功”，还不能确认后续复查已经跑通。

## 4. 交给它第一条 PR

现在可以交付具体任务。工作方法和长期权限已经说明过，这次只需给出 PR 和完成要求：

```text
请持续跟进 <PR 地址>，直到合并、关闭或我明确终止。
沿用刚才确认的权限，为它建立 WorkItem，并订阅该 PR 和 CI 事件。
首次审阅后告诉我：已审提交、阻塞问题、验证结果和下一步。
有新提交时先复查旧问题，再检查新增差异；CI 结果要对应当前 head。
需要等作者修改或 CI 时，保存进度和等待条件。
达到合并条件后向我交接，不要自行合并。
```

打开这条 PR 对应的 WorkItem，应该能找到已审 head、问题与证据、已经完成的验证，以及下一步在等什么。这样，修复到达时 reviewer 可以拿新版本对照上次的阻塞项，不必让你重新整理来龙去脉。

首次结果应当足够具体，例如下面这份示意交付：

```text
已审版本：<head SHA>
阻塞问题：<问题、位置与依据>；或本次未发现阻塞问题
验证：<已执行的测试和结果>；<未覆盖的范围>
下一步：等待 <作者修复 / 当前 head 的 CI / 维护者决定>
```

## 5. 验证一次真正的持续复查

先让现有 CI 跑完，检查 reviewer 是否收到事件、恢复工作并更新检查结果。再等作者提交一次正常更新，验证新版本的复查。期间不用再发“请继续”；观察它是否恢复同一条 PR 的 WorkItem，并更新交付。只收到 CI 完成通知，还没有验证新提交的复查流程。

这一步重点看三件事：

- **版本对上了。** 复查记录写明新 head，引用的 CI 属于这个版本。
- **旧问题有结论。** 哪些已修复、哪些仍存在；新增问题另列，不机械重复上一轮评论。
- **工作状态更新了。** 还在等什么，或者现在需要你做什么决定。

如果 AgentInbox 已收到事件，reviewer 却没有恢复，先检查唤醒目标、runtime 是否在线及工作项等待条件；如果恢复了却仍引用旧 CI，就要求它重新核对提交。补发一句“继续”可以临时推进工作，但不能代替这次接入验证。

前面的 PR #2854 就说明了复查为什么要保留问题明细：第二版解决了旧问题，同时带入另一个错误。记录里需要同时写清“原问题已解决”和“新问题仍阻塞”，维护者才能知道下一步该改哪里。

## 6. 收到交付，再决定是否合并

在本文的保守授权下，reviewer 确认没有遗留阻塞、最终 head 的必要检查通过后，应向你交接，由你执行合并。交付中还应列出未验证的范围，不能把“本次没发现问题”写成代码不存在风险。

PR 合并或关闭后，让它确认终态、记录最终提交，完成 WorkItem，并检查该任务的订阅已经清理。不再使用的 PR 订阅应结束，共享事件源则留给其他工作。

Holon reviewer 的另一条记录里，PR #2856 合并后又收到较早 CI 的迟到通知。它根据保存的终态将通知识别为已处理结果的回声，没有重新开启审阅。工作结束后保留的记录，也帮助它判断哪些变化已经不需要处理。

跑通这一轮后，就可以继续给同一个 reviewer 新 PR。是否增加批准或合并权限，另行说明；创建模板 Agent 并不意味着必须接受自动合并。

## Holon 自身 Reviewer 的近期记录

这套用法也用于 Holon 仓库自身的 `holon-reviewer`。2026 年 9 月 10 日采集的近期记录如下，时间均为 UTC：

| 记录 | 本次采集数量 | 记录时间范围 |
| --- | --- | --- |
| WorkItem | 最近 100 个 | 创建于 8 月 31 日至 9 月 9 日 |
| 结果简报 | 最近 300 条 | 生成于 9 月 7 日至 9 月 10 日 |

这是两组分别取最近 N 条的样本，不是同一时间窗口内的全量统计。WorkItem 数不等于独立 PR 数，一条 PR 也可能产生多条简报；这些数量展示的是工作记录规模，不能用于计算审阅成功率或节省工时。

文中的 PR #2854 使用了完整工作计划及 GitHub 提交、审阅、检查和合并快照；PR #2856 的迟到通知处理来自结果简报，GitHub 快照确认它已合并。本次未重新执行案例中的测试，也未独立验证订阅清理结果。

开始使用时，先选一条低风险 PR：从模板创建 reviewer，补充自己的要求，接好事件，再看它能否在新提交到达后接着复查。等这条 PR 完整交付，再扩大跟进范围。
