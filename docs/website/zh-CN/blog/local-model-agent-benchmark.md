# 本地大模型真能跑通多轮编码 Agent 吗？一次关于 GGUF、轮次膨胀与 Prompt Cache 的实测

在本地终端用 Ollama 跑一句“写个快排”或让模型解释一段报错，几秒钟就能拿到漂亮的输出。单轮盲测榜单上，不少开源模型也屡屡刷出高分（比如 72 题单轮代码盲测里，`qwen3-coder:30b` 拿下了 58/72 的成绩）。这些体验很容易给人一种错觉：桌面级硬件跑本地编码 Agent 已经水到渠成了。

但把同一个本地模型接进真实的工程运行时，画风往往会突变。

在 Holon 这类承载真实仓库工作的运行时里，一次普通的代码修复远不是单轮问答：Agent 首轮就要吞下约 30k Token 的系统与工具契约（文件补丁格式、命令执行规则、工作区权限边界），随后在隔离目录里自己读代码、查调用链、打 `ApplyPatch` 补丁、跑 `node test.js` 验证、看报错修补，最后按契约交付修改摘要。任何一个环节卡壳——首轮预填充太慢、补丁格式打歪、或者反复试探迟迟不收敛——都会直接撞死在任务超时墙上。

为了摸清 64GB 内存级别的桌面设备到底能不能胜任多轮编码 Agent，我们在 Apple M5 Pro（64GB 统一内存）上，用 Holon 仓库自带的隔离基准套件连续跑了两轮基准测试，横向对比了 **5 组本地 Ollama 模型配置**与 **1 组云端基准对照（`deepseek-v4-flash`）**。

跑完数据，我们推翻了自己最初的两个判断：

1. **上一轮本地 27B 模型频频超时，锅不在模型智商，而在推理后端**：同一个 `qwen3.8:27b` 从 MLX 切到 `llama.cpp`/GGUF 路径后，通过率直接从 **3/8 跳到 7/8（底层单测验证 8/8 全过）**。
2. **“单轮代码盲测高分 + MoE 单步吐字快”，在多轮 Agent 里反而可能翻车**：单轮代码盲测拿过 58/72 高分的 `qwen3-coder:30b`（MoE-A3B），虽然把 7 个任务的单测修过了，却因为平均 **23.2 轮**的决策膨胀叠加本地未命中跨轮缓存，单任务平均吞掉 **962k 输入 Token**，最终一半任务折在预算外。

下面是完整的前因后果、测试口径、实测拆解，以及我们基于这组数据整理的本地选型指南。

## 基准演进与测试口径：从“玩具题”到“纯机械判分”

在聊数据之前，有必要交代一下我们这套评测基准的演进背景。

做本地 Agent 评测最怕两件事：一是题目太简单或可以“作弊”；二是拿人工主观打分当结论。
- **v1 阶段（早期玩具题）**：我们曾用简单的单文件修改做测试，结果几乎所有模型都能拿满分；但后来检查日志才发现，部分 Agent 甚至通过 `rg` 在工作区里直接读到了包含预期答案的测试文件。
- **v2 阶段（引入隔离 Harness）**：我们彻底重构了测试套件，把评分规则（测试命令退出码 + 交付约束 `success_criteria`）全部收归 Harness 侧，隔离在受测 Agent 可读取的工作区之外；同时引入 `assertHolonFixtureModel` 校验，确保模型确实产生了真实的推理与工具调用，防止 0 轮空转混过只读检查。
- **v3 阶段（本轮实测）**：在 v2 隔离环境的基础上，我们重点评估不同的本地推理后端（MLX vs GGUF/llama.cpp）以及 MoE 架构在长链路多轮 Agent 中的真实表现。

### 本轮实测约束

- **硬件与推理环境**：Apple M5 Pro（64GB 统一内存，Metal GPU 后端），macOS 26.6.2，Ollama 0.32.15（默认参数启动 `ollama serve`，统一走 OpenAI 兼容端点 `http://127.0.0.1:11434/v1`）。所有受测配置严格串行单跑，避免并发争抢统一内存。
- **隔离 Harness**：使用仓库内置的 `benchmark/run.mjs --runner holon`，每个任务分配独立隔离的 `holon-home` 与测试工作区。
- **任务集与分级预算**：共 8 个真实仓库任务，覆盖代码链路分析（`analyze-pipeline`）、多文件配置合并修复（`fix-multi-file-config-merger`）及其跨轮追问（`followup-after-multifile-fix`）、测试失败重试（`failed-verification-retry`）、带约束修复（`coupon-constrained-fix`、`callback-refactor`）、发票流水线排障（`invoice-pipeline-bug`）以及主从子 Agent 状态巡检（`task-inspection-subagent-status`）。按任务复杂度设 **300s / 600s / 900s** 三档超时预算：预算内同时通过测试与交付检查记 `Passed (P)`，超预算一律记 `Timeout (T)`。

## 发现一：从 3/8 到 7/8，卡住 27B 模型的不是智商，是推理后端

在上一轮（v2）测试里，我们对 `qwen3.8:27b-mlx` 抱有很高期待，结果它只拿到 3/8——剩下 5 个任务全部死在时间上（4 个超时，1 个首轮直接没跑出来）。翻看运行日志才发现，面对 Holon 约 30k Token 的系统提示词，Ollama 当时的 MLX runner 首轮冷启动预填充就要耗掉 **235 秒左右**。代码还没开始读，时间预算已经烧掉了一半。

为了验证这到底是模型能力问题还是推理路径问题，我们在 v3 换了一条路：直接拉取 `ggml-org` 官方的 `Q4_K_M` GGUF 权重（约 19GB，27B Dense），通过本地 `Modelfile` 导入 Ollama 走 `llama.cpp` 后端，原封不动重跑一遍 8 个任务。

结果非常干脆：
- 原先在 MLX 下超时的 4 个任务（`analyze-pipeline`、`coupon-constrained-fix`、`followup-after-multifile-fix`、`invoice-pipeline-bug`）**全部转正为 `P`**；
- 总成绩从 **3/8 跃升至 7/8**，`verify` 底层校验 **8/8 全过**，直接超过此前本地表现最好的 `gemma4:26b`（5/8）。

更有说服力的是两者的过程遥测对比：

- **平均交互轮次**：GGUF 版为 **6.6 轮**，MLX 版为 **6.5 轮**；
- **平均累计输入 Token**：GGUF 版为 **248k**，MLX 版为 **245k**；
- **平均输出 Token**：GGUF 版为 **2.2k**，甚至比 MLX 版（4.2k）更克制。

轮次和输入量几乎重合，直接排除了“换量化格式让模型变聪明了”的解释——模型思考和调用工具的步数根本没变，纯粹是切回 `llama.cpp`/GGUF 后，首轮 30k 冷提示词预填充耗时大幅缩短，原本被卡在半路的正确解法得以在预算内跑完。

唯一没拿到 `P` 的是最后一个任务 `task-inspection-subagent-status`（跑了 2 轮、303 秒撞上 300s 预算墙）。这个任务要求主 Agent 先派生一个受限子 Agent 去扫描模块结构，第二轮再调用状态检查工具汇报子任务结果。在单机本地推理下，主 Agent 和子 Agent 各自都要在同一个本地实例上吃一遍长上下文，300 秒的最短档预算对 27B Dense 模型来说确实太紧了（`qwen3-coder:30b` 也在 304 秒倒在同一堵墙前）。

## 发现二：“每轮吐字快”的陷阱——MoE 模型的轮次膨胀

如果说 GGUF 救活 `qwen3.8:27b` 还在预期之内，那么 `qwen3-coder:30b` 的表现则给我们泼了一盆冷水。

这是一款 17GB 的 MoE-A3B 代码模型（总参数 30B，每 Token 激活约 3B）。在此前的 72 题单轮代码盲测里，它拿下了 **58/72** 的高分，平时交互时单步吐字速度也很轻快。按直觉推演，一个专攻代码又省算力的 MoE 模型，跑编码基准应该如鱼得水。

但真放进多轮隔离基准里，它的最终通过率只有 **4/8**。把 v3 两款模型的逐任务账单拉出来对比，问题一眼就能看穿：

| 任务名称 | `qwen3.8:27b-gguf`（轮次 / 耗时 / 输入） | `qwen3-coder:30b`（轮次 / 耗时 / 输入） |
| --- | --- | --- |
| `analyze-pipeline` | P（10 轮 / 568s / 387k） | P（18 轮 / 473s / 712k） |
| `callback-refactor` | P（7 轮 / 354s / 261k） | E（22 轮 / 473s / 863k，留 `.bak` 脏文件） |
| `coupon-constrained-fix` | P（7 轮 / 386s / 256k） | T（29 轮 / 604s / 1,128k，单测已过） |
| `failed-verification-retry` | P（5 轮 / 246s / 181k） | P（20 轮 / 399s / 766k） |
| `fix-multi-file-config-merger` | P（7 轮 / 469s / 258k） | P（36 轮 / 604s / 1,522k） |
| `followup-after-multifile-fix` | P（4 轮 / 388s / 146k） | P（7 轮 / 728s / 281k） |
| `invoice-pipeline-bug` | P（11 轮 / 661s / 425k） | T（47 轮 / 903s / 2,157k，单测已过） |
| `task-inspection-subagent-status` | T（2 轮 / 303s / 71k） | T（7 轮 / 304s / 264k） |

看明细会发现一个事实：**`qwen3-coder:30b` 并不是不会修代码，它是“做不完”。**

在全部 8 个任务里，它的底层验证（`verify`）其实过了 **7 个**。比如 `coupon-constrained-fix` 跑了 29 轮，`invoice-pipeline-bug` 更是吭哧吭哧跑了 **47 轮、累计吞掉 215.7 万输入 Token**——最后测试其实都修过了，但耗时定格在 903 秒，越过了 900 秒红线被机械判负。唯一没过验证的 `callback-refactor`，它花 22 轮改对了 5 个业务文件，却在目录里顺手留了一个 `src/api.js.bak` 备份文件，撞上任务“不得遗留无关文件”的整洁度约束。

根源在于**单步决策质量带来的轮次膨胀**：
- `qwen3.8:27b-gguf`（27B Dense）看准代码后动手很果断，平均 **6.6 轮**就能完成“定位 → 补丁 → 跑测 → 收尾”；
- `qwen3-coder:30b`（3B 激活参数）单次生成虽快，但在多文件上下文中容易犹豫、拆碎命令、打补丁试错再返工，平均轮次直接膨胀到了 **23.2 轮**——是其他所有受测模型（≤8.5 轮）的 **3 到 4 倍**。

在单轮问答或短任务里，激活参数小意味着低延迟；但在多轮 Agent 循环里，每多犹豫一轮，历史上下文就要重算一遍。**“单轮吐字快”从来不等于“多轮收敛快”。**

## 发现三：本地 Agent 真正的结构性命门——跨轮预填充开销

把总表里的输入 Token 列竖着看一遍，还会看到一个刺眼的数字对比：

- 云端 `deepseek-v4-flash` 跑完 5.6 轮，平均每任务未命中缓存的新增输入只有 **30k Token**，全程耗时 21 秒；
- 本地 `qwen3.8:27b-gguf` 跑完 6.6 轮，平均累计输入 **248k Token**，耗时 422 秒；
- 本地 `qwen3-coder:30b` 跑完 23.2 轮，平均累计输入高达 **962k Token**，耗时 561 秒。

为什么差不多的轮次（5.6 轮 vs 6.6 轮），本地的输入 Token 账单是云端的 8 倍？

关键在于多轮 Agent 的上下文结构与推理栈的 Prefix Cache 复用：
- 多轮 Agent 的开头约 30k Token（系统指令与工具 Schema）是完全固定不变的，每一轮只是在末尾追加新的工具回执与对话。
- 云端 API 普遍开启了服务端 Prefix KV Cache，第 2 轮起前 30k Token 直接命中缓存，只需对末尾几百 Token 做增量预填充。
- 在我们这轮默认开箱配置的本地 Ollama 测试里，由于缺乏跨轮 Prefix Cache 命中（`cache_read_input_tokens` 记录为 0），每一轮都要把前面累积的全部上下文重新做一遍 Prefill。

**Prefill 的计算量是随上下文长度二次方增长的。**
这也是为什么 `qwen3.8:27b-gguf` 平均只输出了短短 2.2k Token，每任务却要跑 7 分钟；而一旦遇上 `qwen3-coder:30b` 这种 23 轮的选手，无缓存重读直接把单任务输入推向百万 Token 级。

不过这也给本地 Agent 指明了优化方向：Ollama 与 `llama.cpp` 本身已开始支持 Prefix Cache（如开启 FlashAttention、保持 Prompt Prefix 严格对齐等）。只要在本地环境里把 Prefix Cache 稳稳配通，本地多轮 Agent 的耗时与轮次容错率将迎来倍数级的改善。

## 私有环境选型指南：今天如何配置本地 Agent 模型？

如果你打算在开发机、内网工作站或离线环境中搭建本地编码 Agent，不需要把所有模型重测一遍，可以直接参考这套经过实测验证的选型方案。

### 1. 本地模型怎么选？

| 你的核心诉求 | 推荐模型配置 | 实测依据与预期表现 |
| --- | --- | --- |
| **主力代码修改（质量与一次收敛优先）** | **`qwen3.8:27b`（`ggml-org` `Q4_K_M` GGUF，约 19GB）** | 7/8 通过、`verify` 8/8 全过，平均 6.6 轮干净收敛；单任务约 5–10 分钟 |
| **日常快修与交互（速度优先）** | **`gemma4:26b`** | 5/8 通过且 **0 超时**，平均 159s/任务，体感响应最轻快，适合常规单模块改动 |
| **后台异步长任务（不卡交互窗口）** | **`qwen3-coder:30b`（17GB GGUF）** | 代码修复底子扎实（`verify` 7/8），但必须放宽单任务预算至 **10–15 分钟以上** |
| **明确不建议用于编码 Agent** | `qwen3.8:27b-mlx`、`qwen3.5:0.8b` 等超小模型 | 前者受困于长提示词预填充耗时；0.8B 量级在 8 任务中 0/8，无法稳定遵循补丁与工具契约 |

### 2. 本地导入 GGUF 必避的两个实操坑

如果你选择表现最好的 `qwen3.8:27b` GGUF 自己导入 Ollama，有两个我们在搭建测试矩阵时踩出来的暗坑值得提前避开：

1. **不要用管道或标准输入传 `Modelfile`**：当前 `ollama create <name> -f -` 从 stdin 读取配置时会**静默失败并返回退出码 `0`**，表面不报错，实则没建好模型。务必先在磁盘写好真实的 `Modelfile` 文件（如 `FROM ./Qwen3.8-27B-Q4_K_M.gguf`），再执行 `ollama create qwen3.8:27b-gguf -f ./Modelfile`。
2. **认准 `ggml-org` 官方量化包**：实测部分第三方量化权重（如 `unsloth` 同款）在导入 Ollama 时会卡在格式校验上，直接使用 `ggml-org` 官方发布的 `Q4_K_M` GGUF 最省心。

导入完成后，如何在 Holon 中把本地 Ollama 设为默认路由、为不同角色 Agent 分配不同模型（例如让主力开发用本地 `qwen3.8:27b-gguf`，架构审查按需切回云端强模型），直接参考[《配置与切换大模型：从本地 Ollama 到多云灾备》](../guides/configure-models.md)。关于隔离工作区与记忆管理的使用说明，详见[《使用工作区与隔离目录》](../guides/work-with-workspaces.md)和[《管理 Agent 记忆》](../guides/manage-agent-memory.md)。

## 下一步测什么

这轮基准测试给了我们一个很踏实的底线结论：**在一台 64GB 统一内存的桌面设备上，选对 GGUF 推理路径的 27B 本地模型，已经能在无人干预的机械验证下独立跑通 87.5%（7/8）的多轮代码修改与测试闭环。**

真正把本地编码 Agent 拦在生产门外的，已经不再是“本地模型看不懂代码”，而是推理后端的冷启动开销、MoE 架构在长链路下的轮次膨胀，以及本地推理栈默认配置下未命中 Prefix Cache 的重算开销。

在下一轮（v4）基准中，我们计划固定模型权重，把**跨轮 Prefix Cache 优化配置前后的真实耗时对比**，以及**本地单机下主从子 Agent 任务的超时归因**单独拆出来实测。跑出新数据后，我们再把账单摊开来聊。
