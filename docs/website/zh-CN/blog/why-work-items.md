# Holon 的 WorkItem 架构：把工作状态从对话中分离

> 中文审阅稿，未发布。下文 reviewer 的两个 PR 是架构演示场景，不是真实运行记录；不包含外部订阅的配置步骤。

## 1. 河水流过，工作留下什么

把 LLM 不断读入和生成的 token 想成一条河。问题、推理、命令输出和修正意见依次流过；其中有些只在当时有用，有些决定了下一步还能不能做对。

一个 reviewer 刚读完几千行 diff，发现了权限检查缺失。作者还没提交修复，另一个 PR 已经需要审阅。等第一个 PR 更新时，最初的分析可能已不在模型的上下文窗口里。即使聊天记录还在磁盘上，也不适合每次都从头读一遍。

WorkItem 像漂在河上的一条船。值得留下的东西需要被打捞上来：这次审阅的范围、发现的问题、对应的提交、还缺什么证据，以及什么时候回来。河水继续流，承载这项工作的记录仍然在。

这个比喻有一个边界：token 流过不等于立刻遗忘，WorkItem 也不会自动识别并保存全部重要信息。这里的“遗忘”指有限上下文、历史裁剪和跨轮重建带来的信息缺口。Agent 需要把关键结论写进持久材料；运行时负责保存这些材料及其调度状态。

于是，问题从“怎样保留更多对话”变成了：**当一轮执行已经结束，系统凭什么知道还有什么工作没做完，又该怎样继续？**

## 2. 把负责人、目标和执行拆开

先给 reviewer 一项明确的委托：审阅 PR #101，跟进修订与 CI，交付最终审阅结论，但不合并。为便于说明，把这项工作记作 A。

在 Holon 中，这不是一个从开始一直运行到结束的模型调用。它由几个寿命不同的对象共同承载：

| 对象 | 在这次审阅中的含义 |
| --- | --- |
| Agent | 持续承担 reviewer 职责的身份；可以同时持有多项未完成工作 |
| WorkItem A | PR #101 的审阅目标、范围与完成边界 |
| turn | 某一轮读取 diff、处理通知或判断下一步的执行 |
| task | 一次受管理的后台执行，例如运行回归测试 |
| 计划、进度和证据引用 | 跨轮保留的审阅发现、已覆盖范围、提交标识和测试结果入口 |

这几层不能共用一个 `done`。测试进程退出，表示 task 有了结果；Agent 本轮结束，表示这轮处理停止；只有约定的审阅目标验收完成，A 才应结束。否则，一次测试成功就可能错误地终结整个审阅。

WorkItem 的持久记录保存 `objective`、生命周期、计划引用和进度等信息。较长的计划正文放在 AgentHome 的 `plan.md`，`todo_list` 保存进度快照，原始 diff 和执行输出保留各自的证据入口。WorkItem 不需要复制整段对话，也不需要装下所有日志。

这个划分还限制了建模粒度。PR #102 有独立的审阅范围和交付结论，值得另建 B；“读取一个文件”只是推进 A 的动作，不必再建一个工作项。短问答或本轮就能结束的小修改，通常也用不到这套跨轮机制。

## 3. LLM 判断下一步，运行时维护可执行状态

Agent harness 不只需要把工具交给模型，还要协调两种不同的判断：模型理解“还缺一次复查”，调度器却必须知道“现在是否允许再运行一轮”。

如果模型只在回复里说“等作者修好后再看”，人能理解，调度器却缺少可执行的条件。它必须猜测这句话是等待、建议，还是已经完成的总结。Holon 用工具调用把这类决定变成结构化状态变化。

![WorkItem 架构：LLM 通过工具写入持久工作状态，调度器结合等待和事件决定后续执行，上下文装配提供恢复依据。](/assets/work-item-architecture-zh.png)

*图 1：调度状态与恢复材料围绕同一项工作组织，但承担不同责任。箭头表示主要信息流，不是线程或进程边界。*

LLM 负责理解目标、分析证据、维护计划，并提出等待或完成请求。运行时校验请求、保存状态，按调度规则决定后续执行。再次运行时，模型读取恢复材料，重新判断业务条件是否满足。调度器不用理解权限漏洞，模型也不用靠一句承诺让自己在未来醒来。

### 为什么一个 status 不够

A 等待修订时至少存在四个不同的问题：

| 维度 | 回答的问题 | A 的一种可能情况 |
| --- | --- | --- |
| 生命周期 | 约定的目标结束了吗？ | 仍然 open |
| 等待条件 | 继续处理前，需要什么信号？ | 等待 PR 更新通知 |
| 续接关系 | 是否主动让出了执行，等另一工作完成后返回？ | 没有；这是外部等待 |
| 当前焦点 | 现在选中的是哪项工作？ | 可能已经是 B，也可能只是在查看 A |

运行时结合这些事实及计划姿态、阻碍信息形成调度投影，对外给出 `scheduling_state`、`readiness` 和 `is_runnable` 等判断。`waiting_external`、`yielded_to_work_item` 不是和 `open`、`completed` 平铺在同一个生命周期字段里的枚举。

这种拆分保留了几个重要区别：

- **选中不等于获准执行。** 查看一个等待中的工作项，不应清除它的等待条件。
- **计划就绪不等于等待解除。** 把 `plan_status` 改成 `ready`，不能代替处理仍有效的等待。
- **唤醒不等于验收通过。** 收到更新通知只意味着值得重新检查，不能据此完成工作。

这也是为什么保存状态与读取状态要采用一致的规则。若调度器认为 A 仍在等待，界面却仅凭“当前选中”把它显示为可运行，模型、用户和运行时就会对同一项工作产生不同理解。

## 4. WorkItem 给上下文裁剪提供边界

调度解决“哪项工作可以继续”，上下文装配解决“继续时让模型看到什么”。只有前者，Agent 会被正确唤醒，却可能不知道自己做到哪里。

假设 B 的处理刚刚结束，最近十轮都在讨论 PR #102。此时 A 收到更新，直接取“最近几轮对话”就容易把 B 的细节带回来，反而漏掉 A 尚未解决的权限问题。把所有历史压成一段摘要，也没有自然的边界来区分两次审阅的结论。

WorkItem 为历史与材料提供归属。恢复 A 时，阅读顺序可以围绕它重新组织：先确认审阅目标和授权范围，再读计划与进度，最后按引用取回本次复查需要的证据。下面是适合留在 A 计划中的记录示意，不是运行时自动生成的固定格式：

```text
目标：审阅 PR #101，跟进修订与 CI；不合并
已审提交：a1（示例标识）
待解决：导出接口缺少租户权限检查
已覆盖：接口入口、鉴权路径；UI 改动尚未复查
证据入口：对应审阅评论、回归测试 task 的结果引用
恢复动作：查询最新 head；若不同于 a1，复查增量与原问题
完成条件：问题已处理，约定检查已确认，交付审阅结论
```

重新查询后，Agent 还要更新这些记录。WorkItem 能保住写下来的进度，不能替一份过时的计划保证正确。

这也不意味着上下文已经被彻底隔离。当前实现提供 `work_item_scoped` 历史选择路径：从候选轮次中按 WorkItem 归属筛选，再在预算内装配。默认仍是 `recent_turns`；当提供方能力或所需投影不可用时，按工作项选择的路径也会回退。它并非自动检索全部历史，更不保证每次都选到最优信息。

这里真正获得的是一个可用的裁剪依据：**旧对话可以不再完整进入提示词，未完成目标及其恢复入口仍有独立记录。** 它比单纯扩大窗口更适合表达工作连续性，但仍依赖 Agent 及时保存关键材料。

## 5. 一个 reviewer，两个交错的 PR

现在把各层放进同一个场景。A 是 PR #101 的审阅，B 是 PR #102 的审阅。下面假设已配置外部事件投递；图中展示的是一种合法的执行顺序，不代表固定优先级。

![reviewer 双 PR 时序：A 等待修订，Agent 转去审阅 B；A 的通知到达后，B 先保存进度并等待自己的测试，随后恢复 A，B 仍保持未完成状态。](/assets/work-item-reviewer-sequence-zh.png)

*图 2：两项工作的生命周期重叠；模型处理按轮次交错。A 的通知不会把 B 自动标成完成，也不表示立刻抢占正在执行的工具。*

### A 等修订时，B 可以开始

reviewer 在 A 中发现权限问题，保存审阅进度后登记等待。下面是工具调用示意，不是 shell 命令；`A` 应替换成实际工作项 ID：

```text
WaitFor(wake="external", resource="github:example/repo#101",
        work_item_id="A", reason="等待作者提交权限检查修复",
        recheck_after_ms=900000)
```

`WaitFor` 保存等待条件并让出执行。A 仍然 open，但不应无事可做地反复调用模型。另一个审阅请求到来后，reviewer 可以为 PR #102 建立 B，并开展审阅。

这里的 `resource` 只是等待对象的引用，不会替用户创建 GitHub 订阅，也不是“只接收 #101 且修复已通过”的业务过滤器。事件投递必须另外配置。十五分钟回查是兜底，不是作者必须完成修订的期限。

### A 更新时，B 的工作怎么办

处理 B 期间，A 的新提交通知到达。运行时记录对应的唤醒信息；这不意味着立即打断正在运行的模型或工具，把它的执行现场搬到 A。

在图示的这次流程里，B 已完成初步分析，并启动了后台回归测试。reviewer 保存 B 的发现、未检查范围和测试 task 引用，然后用 `WaitFor(wake="task_result", resource="T_B")` 等待结果。B 因此也有了明确的恢复条件。

当执行让出、调度条件允许时，A 可以进入后续处理。B 不会消失：它的目标仍未完成，测试等待仍归属于 B。之后测试终结，运行时再根据对应结果安排 B 的恢复。

因此，这里的并发首先是**同一个 Agent 同时持有多项未完成工作**。外部 CI 或后台命令可以并行执行，但不能据此理解为同一个 Agent 正同时运行两个模型轮次。

### 回到 A，先查事实，再决定是否结束

如果接入采用 `wake_hint`，通知只提示有变化，不把载荷变成模型消息。reviewer 恢复 A 后，应读取它的进度记录，查询 PR 当前 head 和检查结果，并确认原权限问题是否已解决。

旧 CI 通过，不代表新提交通过；通知也可能重复，或根本没有带来可用的新证据。如果仍需等待，就重新登记条件。如果问题已解决且约定检查完成，再交付审阅结论。由于原委托不包含合并，不能顺手把“审阅完成”扩大成“合并 PR”。

对于 B 的本地 task，还有另一类竞态：测试可能在 `WaitFor` 登记之前就已经结束。运行时会检查任务结果的终结、投递与消费状态，而不是只等待未来发生的完成事件。这避免了“结果早到了，等待却永远等不到”的一类问题；它不等于所有外部通知都能得到同样的保证。

### 主动让出是另一种关系

以上 A、B 都在等待各自的条件，没有 A 等 B 完成的依赖。另一种情况是：A 仍可运行，却需要先处理独立工作 B。此时通过 `PickWorkItem(B)` 主动切换，可以记录 A → B 的续接关系：A 暂时 yielded，B 完成后恢复 A。

两种情况不能混用。外部等待应记录“等什么信号”，主动让出应记录“做完哪项工作后返回”。若把等待 PR 修订的 A 错记成让出给 B，就可能在 B 完成后过早恢复 A；若把续接伪装成外部等待，又会丢掉返回关系。

## 6. 工作如何结束，以及哪些事仍不能保证

经过几次等待，A 的审阅终于完成。此时运行时需要同时留下“责任已经结束”和“交付了什么”，不能只改一个标签。

`CompleteWorkItem` 将非空交付报告绑定到本次执行、工作项版本和完成请求，再提交完成状态、结果 brief、焦点与等待清理，以及必要的续接效果。仅调用工具却没有报告，不应被当成已经完成交付。对 A，报告需要说明审阅的提交、问题处理情况、检查结果与剩余限制。

这里完成的是 A。B 的测试等待不因 A 结束而解除，B 也不会被一并完成。反过来，如果 A 的报告仍写着“后续继续跟进”，就要检查原目标是否真的结束：尚未履行的责任必须有未完成工作或明确的后续安排承载，不能只留在结尾一句话里。

WorkItem 提供的是可恢复的工作组织方式，不是“不丢任何工作”的绝对保证。没有保存的发现仍可能丢失；外部事件可能漏投；文件和远端状态可能在等待期间改变。完成状态与报告绑定，也不等于外部副作用 exactly-once，更不保证任意崩溃后都能无损恢复。重新执行前，Agent 仍需核对证据与当前状态。

这些边界解释了为什么 WorkItem 既不是待办列表，也不是对话摘要：它把目标、恢复材料和调度依据联系起来，使一次暂停之后，运行时还有可查询的责任，模型还有可读取的下一步依据。可靠性来自持续维护这些记录与状态转换，而不只是“把聊天存下来”。
