# 文档分层

Holon 的文档分成四层，边界清晰。这样可以避免用户看到的内容、运行时的真实
行为和维护者正在设计的内容之间出现漂移。

## 第 1 层：产品网站（`docs/website/`）

**读者：** 新用户、评估者、集成方，以及正在了解 Holon 的贡献者。

**目标：** 解释 Holon 为什么存在，引导用户完成第一次成功使用，并在不让读者
被 RFC 细节淹没的前提下讲清足够稳定的概念。

**结构：**

| 部分 | 作用 |
|---------|---------|
| 首页 | 产品承诺、面向人群、品牌层级、第一个行动入口 |
| 快速开始 | 从 clone 到第一次与 Agent 交互的最短路径 |
| 概念 | 在深入生命周期词汇之前，先讲四对象心智模型 |
| 指南 | 按用户任务分组的工作流 |
| 参考 | 当前契约的 CLI、配置和控制平面快照 |

**规则：** 网站页面解释*是什么*和*怎么做*，不解释*设计为什么是这样*。设计
理由用链接指向 RFC。

## 第 2 层：运行时规格（`docs/website/spec/`）

**读者：** 需要了解当前运行时契约的维护者和贡献者。

**目标：** 描述当前面向实现的契约——Holon 今天实际做什么，并对照实现和测试
验证。

**规则：** 规格页面不是用户教程，而是权威契约。每个规格页面都链接到促成该
设计的源 RFC，并跟踪已知的实现/RFC/测试缺口。运行时行为变化时，规格页面和
RFC 应一起更新。

## 第 3 层：当前公开契约

**读者：** 运行、配置、集成或排查 Holon 问题的用户。

**目标：** 描述当前行为。明确标出实验性或不稳定的行为。

**包含：**

- `docs/website/reference/` — CLI、配置和 HTTP 控制平面页面
- `README.md` — 仓库高层入口和贡献者指引
- `docs/website/spec/` — 当前面向实现的契约
- `docs/runtime-spec.md` — 把最初的 v0 规格映射到各细分规格页面的汇总索引
  （不是用户教程）

**规则：** 参考页面应针对编译后的运行时（`holon --help`、`holon config schema`）
验证。标出每页最后核对的版本。如果行为是实验性的，就明确说明。

## 第 4 层：维护者设计（`docs/`、`docs/rfcs/`、`docs/implementation-decisions/`）

**读者：** 修改运行时语义的维护者和贡献者。

**目标：** 保存架构契约、设计理由和历史决策。这些是运行时行为的权威事实来源。

**结构：**

| 位置 | 内容类型 |
|----------|-------------|
| `docs/rfcs/` | 规范设计契约——每个运行时概念一份 RFC |
| `docs/implementation-decisions/` | ADR 风格记录——每个文件一个决策 |
| `docs/archive/` | 已取代的说明和历史设计文档 |

**规则：** 运行时概念变化时，先更新 RFC。实现决策记录*为什么*做了某个选择。
归档保存历史，但不弄乱活跃的文档面。

## 跨层链接

- 网站页面把 RFC 作为“更深入的设计背景”链接，而不是必读材料。
- 仓库 `README.md` 链接网站作为产品入口。

## 何时更新哪一层

| 变化 | 主要目标 | 次要目标 |
|--------|---------------|-----------|
| 新增 CLI 命令 | 参考页面 | 指南、快速开始 |
| 配置键变化 | 参考页面、配置 schema | 站点中的参考页面 |
| 运行时概念变化 | RFC | 概念页面、参考 |
| 新用户工作流 | 指南 | 快速开始 |
| 产品信息 | 首页 | README |
| 设计理由 | 实现决策 | 若具规范性则写 RFC |
