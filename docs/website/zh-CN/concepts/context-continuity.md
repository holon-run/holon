# 上下文连续性

上下文连续性使 Agent 能够借助持久保存的工作状态和相关证据，跨越多次激活持续推进同一个目标。每次模型调用接收到的上下文视图都是有界的，运行时并不会重放全部历史流水，也不会反复加载 Agent 曾经阅读过的所有文件。

例如，在等待 CI 完成后，Agent 需要的是最初的验收标准、受测的代码版本以及最新的 CI 构建结果，通常并不需要之前执行过的每条 shell 命令的完整原始输出。

## 模型可见的上下文结构

一次激活的上下文通常包含：当前输入及其来源元数据、正在延续的目标、当前工作状态、相关的近期执行结果、筛选出的历史证据，以及带有指引文件的执行环境。

活动工作项是记录当前目标、计划和进度的权威来源。早期的历史摘要有助于说明工作是如何推进到当前阶段的，但它们不能覆盖已经更新的执行范围或操作者最新的决策。当需要确认精确细节时，Agent 应当重新调阅引用的原始证据。

## 将结果准确关联至对应请求

任务结果可能会在 Agent 处理完另一条消息后才返回。Holon 会始终将执行结果与发起时的调用及工作项归属绑定在一起，以便它能准确延续对应的请求。新的外部事件不会自动变成新的操作者目标。

正因如此，CI 构建的完成通知能够准确导回最初触发该次构建的工作项。在采纳结果之前，Agent 仍必须核对该次构建与代码版本是否与预期相符。

## 有界上下文与信息召回

运行时会智能提炼当前工作与有效证据，而不是简单堆砌不断膨胀的聊天记录。较早期的工作通常以摘要和引用的形式存在。因此，部分历史细节可能不会直接出现在当次 prompt 中。

摘要保留了回溯原始证据的路径，但摘要本身既不是独立的授权凭证，也不能替代正式的工作记录。外部输入被总结之后，其不可信性质依然不变。[记忆系统](./memory.md)详细说明了哪些内容可以被检索，以及哪些文件会被自动加载。

## 支撑有效恢复的关键记录

工作项应当完整保留范围定义、决策结论、验收标准以及下一步行动。任务句柄标识单次执行及其返回结果。完成报告阐述交付结论与验证状态。产物引用则准确指向文件实体，包括包含该文件的具体 worktree。

有了这些持久记录，Agent 在恢复工作时就无需假设自己“还记得”之前的对话。像“继续修”这样模糊的计划无法提供有效指引；仅输出一段最终答复，也无法替代对未完工目标的显式状态更新。

## Holon 如何维持工作的连续性

请区分以下三种中断情况：

| 中断类型 | 系统表现与预期 |
|---|---|
| 客户端断开连接 | 守护进程接管后台运行任务，在其持续运行时能正常推进。重新连接客户端即可查看状态与结果。 |
| 守护进程停止或重启 | 持久保存的目标与证据支持系统恢复。恢复后应先检查当前状态，不要盲目假定执行已自动恢复。 |
| 命令或模型请求中断 | 检查已记录的执行结果与可能产生的副作用，再决定是否重试。意图被持久化并不保证底层进程不会中断。 |

重新连接后，应当从当前工作项和任务状态开始排查，不要假设之前运行的所有进程都完好无损。对已经修改了外部系统的操作进行盲目重试，可能会导致外部状态产生重复变更。

## 面向用户的系统契约

你可以依赖明确的工作记录与来源追踪来弄清 Agent 正在推进什么；但你不应当期望系统拥有无限的记忆召回、对全部历史流水的完整重放，或者在发生意外中断后能够完全免人工干预地自动达成目标。

对于需要稍后恢复的工作，务必妥善记录目标与验收标准，通过运行时登记等待，并将所需产物保存在持久目录中。如果证据缺失或进程失败，Agent 应当如实说明情况并指出具体的恢复步骤。
