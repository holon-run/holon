# 在自己的电脑上运行常驻 AI 助手

你已经在本机跑着本地模型——Ollama、vLLM 或其他 OpenAI 兼容端点——并在终端或聊天窗口里与它对话。本指南讲的是下一步：从「能与本地模型对话」到「自己电脑上的常驻助手」，中间还缺什么，以及如何在不放弃本地模型的前提下，用 Holon 补上这一段。

缺的不是模型，而是模型周围的一切：一个让任务活得比聊天窗口更久的地方、一种让 Agent 按计划唤醒而不是只等你按下回车的机制、以及离开桌面后从另一台设备核对结果的途径。下面依次覆盖前提条件、与本地对话的具体差异、手机客户端能做什么不能做什么，以及一套你可以自己执行的验收。

## 开始之前

- 主机可达的本地模型服务，例如 `http://127.0.0.1:11434` 的 Ollama，或 vLLM / OpenAI 兼容端点。如需严格的纯本地边界，从[离线私有环境指南](./run-offline-private-agent.md)开始。
- 一台无人值守期间保持开机的宿主机：台式机、小主机或服务器。如果守护进程跑在你随身携带的笔记本上，合盖休眠期间不会有任何工作执行——Holon 不会唤醒已挂起的主机。
- 正在运行的 Holon 守护进程，[Web GUI](./use-web-gui.md) 已打开且[模型路由已配置](./configure-models.md)。
- 可选：已配对的 [iOS](./connect-ios-client.md) 或 [Android](./connect-android-client.md) 客户端，以及从桌面网络之外访问守护进程的网络通路（参见[连接远程运行时](./connect-remote-runtime.md)）。

## 第 1 步：确认你现有的本地环境能提供什么

交付真实工作前，先做两个检查。

首先，确认宿主机上模型服务有响应：

```bash
curl http://127.0.0.1:11434/api/tags
```

对 Ollama 而言，这条命令返回已安装的模型列表。如果失败，先修复模型服务；任何助手层都无法弥补一个不可达的模型。

其次，把 Agent 的默认模型路由到本地模型，并把 fallback 策略显式定下来：

```bash
holon config set model.default "ollama@default/your-model"
holon config providers list
```

如果宿主机上存在云端厂商凭据且 fallback 保持开启，一次缓慢或失败的本地调用可能静默切换到云端 Provider。如果不希望这样，关掉它：

```bash
holon config set runtime.disable_provider_fallback true
```

然后在对话中核实真正应答的模型是谁：

> "做一个不改任何文件的路由自检：报告你当前的 `model.requested_model`、`model.active_model` 和 `model.fallback_active`。"

`model.active_model` 应与你的本地路由一致；关闭 fallback 后 `model.fallback_active` 应为 `false`。关于哪些本地模型能跑完多轮 Agent 任务，参见[本地模型实测](../blog/local-model-agent-benchmark.md)。

## 第 2 步：给工作一个活得比聊天窗口更久的地方

在 Web GUI 对话中，把带验收标准的目标交给 Agent，并要求它用独立 WorkItem 跟踪：

> "用独立 WorkItem 跟踪这件事：<你的目标与验收标准>。先写计划等我确认，再后台执行，完成时给我报告。"

与你现有的聊天窗口相比，四件事发生了变化：

- **你离开后谁在继续执行。** 守护进程托管后台命令任务；Agent 在步骤之间休眠，不消耗 Token，一切不依赖你的终端或浏览器标签页保持打开。
- **任务状态存在哪里。** WorkItem、计划与检查清单持久化在宿主机上，守护进程重启、主机重启后依然存在。
- **在哪里核对结果。** 同一个 WorkItem 与完成简报对 Web GUI 和手机客户端都可见，不绑定于发起工作的那个会话。
- **失败后怎么办。** 只从记录的检查清单重试失败的那一步；重放整段对话不是恢复路径。

[运行长生命周期任务](./run-long-lived-task.md)给出完整工作流。两条边界直说：

- 这不是 7×24 可用性承诺。只有在主机开机、守护进程运行时，工作才会继续。
- 周期性工作可以通过[定时器与计划唤醒](./schedule-agent-work.md)推进；已挂起的主机依然什么都不会执行。

## 第 3 步：分清手机客户端能做什么、不能做什么

手机客户端是同一运行时的窗口，不是第二个大脑。Agent 跑在你的宿主机上；手机负责渲染对话、简报与文件，并把你的输入送回去。离开桌面前，先对照这张表：

| 你想做的事 | 离线可用吗 | 失败时检查什么 |
| --- | --- | --- |
| 阅读已同步过的对话 | 可以，受应用缓存上限约束 | 缓存文本只是快照，不能证明运行时可达 |
| 打开简报中引用的文件或产物 | 不行，需要在线连接 | 缓存简报不会缓存关联文件，先恢复连接 |
| 发消息、批准计划、停止运行 | 不行，需要守护进程可达 | 请求可能停留在发送队列（iOS）或离线发件箱（Android）中；恢复连接后先检查队列再重发 |
| 从其他应用分享内容给 Agent，或离线撰写提示词 | 暂存而非执行 | iOS 存入 Share inbox、Android 进入离线发件箱，重连后才会送出；送出前先核对队列 |
| 启停宿主机守护进程、守护进程级诊断 | 客户端不提供 | 回到宿主机操作。客户端的「诊断」只覆盖连接状态与客户端版本 |

核对结果时，区分三种状态：**对话已同步**（你能读到）、**产物能打开**（引用的文件在运行时上真实存在并可解析）、**完成简报已生成**（Agent 报告的是结果，而不只是活动）。配对与平台细节参见[连接 iOS 客户端](./connect-ios-client.md)与[连接 Android 客户端](./connect-android-client.md)。

## 第 4 步：跑一次你自己的验收

挑一个真实任务：至少跨数小时、产物可核验，例如一套跑得慢的测试或一批待处理的文件。然后离开：

1. 在 Web GUI 对话中给出带验收标准的目标，要求 Agent 用 WorkItem 跟踪、后台执行、完成时报告。
2. 关闭浏览器标签页，离开桌面（保持守护进程所在主机开机）。
3. 从手机或另一台机器打开客户端，检查工作进展。
4. 可选：任务中途重启一次守护进程，确认它回来后 WorkItem 仍在且状态完好。

| 检查项 | 通过标准 |
| --- | --- |
| 任务在你离开后仍在推进 | WorkItem 展示同一份计划与检查清单，且进度在你离开期间有前进 |
| 结果是真实的 | 从另一台设备上，产物或文件引用能解析并打开 |
| 完成有报告 | 存在完成简报，并链接变更文件或输出 |
| 恢复是有边界的 | 守护进程重启后 WorkItem 状态完好，只有未完成的里程碑需要重跑 |

没有通过时，几乎总是以下三层之一：

- **主机睡着了。** 挂起期间不会有任何执行。调整主机电源设置；WorkItem 状态已保留，恢复后工作继续。
- **本地模型超时或报错。** 在 Agent 自检里看 `model.fallback_active`：若 fallback 开启且宿主机有云端凭据，这次运行可能已切换到云端 Provider。只重试失败的那一步。
- **手机连不上守护进程。** 属于网络通路问题：本地网络权限、tailnet 或反向代理。参见[连接远程运行时](./connect-remote-runtime.md)与[故障排查](./troubleshooting.md)。
