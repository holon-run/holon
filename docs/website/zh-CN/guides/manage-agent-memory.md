# 管理 Agent 记忆：从长期偏好沉淀、原始历史检索到过期记忆核验与纠偏

长生命周期的 Agent 需要在跨越多个工作会话、客户端断开重连或数周的工作流中，持续记住你的编码风格、审查偏好与稳定项目事实。然而，许多 Agent 系统要么在对话上下文拉长后频繁遗忘，要么因为盲目将所有历史总结成模糊的摘要，在面对复杂推导和细节时丢失因果依赖，甚至产生严重的过时记忆冲突与幻觉。

在 Holon 中，记忆管理由**显式精选记忆**（Explicit Memory）与**强原始历史检索**（Raw History Retrieval）双层架构协同驱动。你可以直接在 Web GUI 或终端对话中，用自然语言让 Agent 记录习惯偏好、通过底层证据检索回溯历史决策依据，并在环境变更时快速核验并纠正过期记忆。

## 前置条件

- 正在运行的 Holon 运行时与 [Web GUI](./use-web-gui.md)（默认地址 `http://localhost:8080`）或 CLI 环境。
- 一个处于活跃状态的长生命周期 Agent（例如 `main` 或自定义 Agent）。
- 无需手动编写复杂的向量数据库脚本或手动修改底层数据库：所有记忆管理均可通过自然语言在对话中驱动完成，或在 Agent 的配置目录中直接查看 Markdown 文件。

---

## 操作步骤

### 1. 理清记忆分层与权责边界

高效管理记忆的前提是明确不同信息的归属层级。Holon 明确划分了显式记忆、原始历史检索与行为契约的边界：

| 信息类别 | 存储载体 | 加载机制与设计意图 |
|---|---|---|
| **操作者偏好与风格** | `memory/operator.md` | 每次会话自动加载前 1500 字符切片。记录操作者语言习惯、代码审查偏好、PR 检查要求等。 |
| **Agent 自身状态与事实台账** | `memory/self.md` | 每次会话自动加载前 1500 字符切片。记录该 Agent 自身负责的领域、长期追踪的关键指标基线、外部依赖台账等。 |
| **底层原始历史证据** | 运行时事件与 WorkItem 记录（`MemorySearch` / `MemoryGet`） | 按需动态检索，不占用常驻上下文。包括历史对话消息、工具执行收据、工作项计划与验收凭据。 |
| **常驻准则与授权边界** | Agent 与项目工作区的 `AGENTS.md` | 每次请求全量加载。定义 Agent 的职责角色、不可逾越的安全红线与需要人工授权的升级边界。 |
| **当前任务状态与执行流** | 运行时工作项（WorkItem） | 调度核心。记录当下具体任务的目标、步骤与等待状态。记忆绝不能替代任务的实时状态。 |

> **研究洞察：为什么显式记忆需要强原始检索作为对照底本？**
> 生态研究（如 arXiv:2610.30755 与 arXiv:2610.24671）表明，将长历史一律压缩抽取为高层摘要或知识图谱，极易在“建记忆”阶段丢失复杂推导所需的因果关联与上下文细节（即“建记忆丢证据”）。因此，Holon 保持显式记忆精简高信噪比，在需要准确事实和历史依据时，强制让 Agent 回查不可篡改的底层原始事件与工作项记录。

---

### 2. 在自然语言对话中沉淀长期偏好

你无需手动去文件系统中寻找路径。在日常协作中，直接向 Agent 发送你的工作偏好即可：

**操作者对话示范**：
> “请记住我的日常协作习惯：  
> 1. 回复与交付简报统一使用中文；  
> 2. 在项目文件中提交代码前，必须先在本地运行静态校验和最小测试集；  
> 3. 代码中的错误提示必须附带具体的上下文参数，不要只打印模糊的错误字符串。”

**Agent 的内部响应与执行**：
Agent 会识别该指示属于稳定的操作者偏好，通过工具自动将这些偏好追加或更新到 `agent_home/memory/operator.md` 中：

```markdown
# Operator Memory

- 默认使用中文进行回复与交付简报。
- 提交代码变更前，必须运行本地静态校验与最小验证测试。
- 错误信息必须携带具体的上下文参数，禁止输出模糊的无参数报错。
```

下次无论是新开对话轮次还是重新启动运行时，这些偏好都会作为高优先级精选切片自动载入，无需每次重复强调。

---

### 3. 利用原始历史检索回溯决策证据（避免凭模糊记忆臆测）

当需要回顾过去的架构决策、故障排查原因或代码变动背景时，要求 Agent 从原始记录中进行检索，而不是盲目相信可能失真的多轮摘要。

**操作者对话示范**：
> “上周我们在重构调度模块时，讨论过是否引入方案 B（事件总线集中分发），请帮我检索当时放弃方案 B 的具体原因和讨论证据。”

**Agent 的证据检索流程**：
1. **定位事实证据**：Agent 调用 `MemorySearch` 检索关键词（如 `方案 B 事件总线 调度重构`），定位到历史会话、工作项简报及工具调用记录；
2. **精确切片回读**：针对命中的证据引用（`source_ref`），调用 `MemoryGet` 提取确切的上下文；
3. **向操作者交付可追溯报告**：

> “根据 2026-11-09 工作项 `work_38a19` 的讨论记录与对比结论，当时放弃方案 B 的主要原因如下：  
> 1. 集中事件总线引入了跨进程锁竞争，在并发模拟测试中导致唤醒延迟上升 35%；  
> 2. 会破坏现有运行时进程隔离的信任边界划分。  
> 原始记录索引参考：`brief_84f910a` 与 `turn_129`。”

这种基于原始证据的检索回查，从根源上杜绝了语言模型在长周期记忆中的幻觉与以讹传讹。

---

### 4. 核验与纠偏：修剪过期或冲突的旧记忆

随着项目演进，过去的习惯与技术栈可能会发生重大变化（例如：团队从旧的本地构建脚本切换到了统一的 Docker/CI 流水线，或者废弃了某项工具）。如果任由旧记忆堆积，Agent 就会陷入新旧规则冲突。

通过对话让 Agent 主动核对并纠正过期记忆：

**操作者对话示范**：
> “检查你当前记忆中关于构建和部署的规则。我们现在已经全面停用本地部署脚本 `deploy.sh`，改由 GitHub Actions 自动部署。请清理过期规则并更新偏好。”

**Agent 的核验与纠偏动作**：
1. **自检现有显式记忆**：检查 `memory/operator.md` 与 `memory/self.md` 中与“构建/部署”相关的条目；
2. **识别冲突与失效项**：发现旧条目 `- 每次发布前需在本地运行 ./scripts/deploy.sh staging 验证` 与当前事实冲突；
3. **精准修剪与合并**：修剪掉旧脚本条目，写入新的 GitHub Actions 流程，并向操作者汇报变更差异：

> “已完成记忆核验与纠偏：  
> - **已移除过期条目**：`每次发布前需在本地运行 ./scripts/deploy.sh staging 验证`；  
> - **已更新条目**：`代码合并推送到 main 后，等待 GitHub Actions 自动触发部署，并跟进线上健康检查`。  
> 记忆文件已更新，当前字符数保持在安全加载预算内。”

## 保持记忆高信噪比的最佳实践

1. **严守 1500 字符切片预算**：
   `memory/operator.md` 和 `memory/self.md` 的设计初衷是承载**高频、长期稳定、高信噪比**的规则。避免将大量临时工作清单、一次性日志或整篇文档塞入记忆文件中。超过预算的内容虽然可通过搜索召回，但无法常驻首屏。
2. **区分“偏好”、“准则”与“任务进度”**：
   - 属于通用习惯的，放入 `memory/operator.md`；
   - 属于安全底线与执行权限的，写入 `AGENTS.md`；
   - 属于当前正在攻坚的具体任务的，使用 `WorkItem` 记录目标与 Todo 状态，任务完成后标记结束，绝不沉淀为永久记忆。
3. **记忆永远不可超越授权边界**：
   记忆属于辅助事实上下文。即使 Agent 记忆中记录了“操作者允许自动化发布”，涉及资金、不可逆删除或生产环境发布的重大动作，如果 `AGENTS.md` 中规定了升级确认，Agent 仍必须停下来向操作者获取显式授权。

## 常见问题与排障

### 为什么 Agent 似乎没有遵守我刚才交代的新偏好？
- **检查是否写入正确文件**：在对话中询问 Agent：“请列出你当前加载的 operator memory 内容”，确认偏好是否已实际持久化到 `memory/operator.md`。
- **检查是否存在新旧记忆矛盾**：若未清理旧条目，Agent 可能在新旧规则之间摇摆。直接指示 Agent：“清理旧偏好 X，以后只遵循新偏好 Y”。
- **检查是否超出切片预算**：若记忆文件过长（超过 1500 字符），末尾部分会被自动截断，需通过检索或精简前置内容才能生效。

### 什么时候该用自然语言记录，什么时候该直接编辑文件？
- **推荐自然语言交互**：在日常使用中直接对话说明最快捷，Agent 会自动保持格式规范并合并同类项。
- **直接文件编辑**：当需要做大规模重组、批量导入已有规范或审核敏感条目时，可以直接打开 Agent Home 目录下的 `memory/operator.md` 和 `memory/self.md` 进行 Markdown 格式编辑。
