# Agent loop 与 TaskResult 处理的简化方案

2026-11-14 · 讨论稿，非规范性 · 代码基线 `origin/main` `90811078`

这篇是供讨论的方案，不是已接受的设计。它回答一个问题：怎样让 agent loop 和 TaskResult 的注入、处理这套逻辑更容易推理，从结构上减少 #4074 这类缺陷。

#4095 和 #4101 已经修掉了直接的缺陷：`Defer` 改为窄写，无法推进的结果不再每 30 秒写库，两条没有出口的状态有了结局。这篇讨论的是这些缺陷背后的结构，目标是让下一次同类问题在设计上不容易出现。

方案的核心是三件事：

1. **一个结果的“下一步”只由一个函数决定。** 它是纯函数，对所有状态组合给出结论，每个结论要么是投递、结算，要么是带明确触发条件的等待。
2. **等待由事件驱动。** 重新判断只发生在相关事实变化时，触发条件是一个封闭的集合。
3. **loop 只做“事件 → 决定 → 应用”，常驻视图与请求形状和时间无关。** 空闲的 agent 不读库也不写库。

这不是新的调度器，也不是新的架构。[Scheduler–WorkItem Unified Execution Protocol](../rfcs/scheduler-work-item-unified-execution-protocol.md) 已经为执行准入定下了“每个问题只有一个权威”的原则。这篇做的是把同样的原则落到两处还没有覆盖的地方：结算账本及其恢复扫描，以及 loop 本身。达成一致后，契约变更应以 RFC 修订的形式落到 `docs/rfcs/`。

## 暴露出的结构问题

证据来自 #4074 的复核评论和 #4094。每一条先说事故时的表现，再说 #4101 之后还剩什么。

### 结算账本成了第二个调度器

统一执行协议规定，结算账本“而不是第二个执行或唤醒权威”来记录待处理、已准入和已结算的责任，不合格的 owner 让结算“持久延期，并有一个有界的恢复入口”。

实现里，恢复扫描（[emit_due_task_result_recovery](../../src/runtime/task_result_recovery.rs#L738)）自己做了一遍调度：逐条判断资格，决定延期、结算还是入队唤醒。事故时它每 30 秒为每条无法推进的结果写一条持久化的 `Defer`，没有上界；恢复预算只约束实际 admission。线上 94 条结果的重检需求约是 writer 全部容量的 4 倍。

#4101 之后，无法推进的结果改为在内存里退避，相关的 Work、Wait、执行通道变化会提前唤醒它（[wake_task_result_probes](../../src/runtime/task_result_recovery.rs#L110)）。写入问题解决了，但扫描仍然是一个独立的调度阶段，并且多了一层状态：一条等待中的结果现在同时由持久化的期限、内存里的探测记录和已发布的元数据描述，三者需要保持一致。

### 同一个问题有很多处在回答

“这条结果现在能不能投递、投给谁”分散在约 12 个函数里：义务分类、回复来源是否可恢复、被丢弃回复是否匹配、精确 waiter 的续接、锚点 turn 是否存活、扫描里的一串检查，以及调度认领。调度认领另有 9 种激活场景和约 30 个 `canonical_*` 拒绝原因。

这些地方各自正确，但没有任何一处能保证组合起来是完整的。事故中的两条死路都是组合上的遗漏：

- **被丢弃的回复**：调度认领因为 WorkItem 不可运行而丢弃了回复，结算义务按契约保留，只允许精确 waiter 认领；扫描则认为“原始队列项仍拥有首次投递权”。三处规则合在一起，没有 waiter 的结果永远没有出口。线上有 73 条，最早的已经四周。
- **`invalid_or_stale`**：义务分类返回这个结果后，扫描直接延期，走不到同一函数后面“owner 已关闭则结算”的分支。

#4101 给这两种情况各补了一个出口，并让回复在 owner 等待期间留在队列里。这是在原有结构上增加分支：扫描里多了收敛操作和三个新的原因字符串，判定函数的数量没有减少，也仍然没有一处能证明组合是完整的。

open issue 里还有几个从标题看是同一形态的问题：状态卡住没有出口（#3914、#3927、#3846），或者守卫失败变成不可重试的中止（#3963、#3975、#4052）。这几个只看了标题，没有逐个核对。

### 常驻快照按请求形状发布

每个 agent 的 Task 域只有一份已发布的 coverage，它记录的不只是事实，还有上一个调用方的请求形状：`required_keys`、terminal 窗口大小、查询选择，以及一个时间戳 `recovery_at`。约 12 个子系统用不同的形状请求它，形状不匹配就在写事务里全量重建。

事故中观察到的翻转就是这样产生的：调度读只要有恢复来源就带一个新的 `recovery_at`（[work_planning.rs](../../src/runtime/state_mutation/work_planning.rs#L328)），复用条件要求时间戳相等（[task_preparation.rs](../../src/runtime/state_mutation/task_preparation.rs#L345)），所以每次都重建；重建后的形状又让 #4095 的窄 `Defer` 路径不命中，回退再把形状写回去。对一个 agent 的持久化 coverage 采样，每个循环周期固定三次全量重建。

这两处代码在基线上没有变化。#4101 让扫描自己的准备改为直接复用已发布快照，调度读的路径没有动。

### 读、校验和重建都在写事务里

一次 Task 域重建在线上是 0.7–6 秒，随 agent 的历史增长。它发生在全 Host 共享的写事务里，并且是逐 Task 的多次查询。#4101 把扫描的 Queue 观测移到了只读事务，Task 域重建本身仍在写事务里。

### 规模

`src/runtime/` 约 15.6 万行，`src/runtime_db/` 约 18.4 万行（不含测试），调度执行器 7,200 行，`host.rs` 3.3 万行，运行库有 165 张表。这和 `AGENTS.md` 里“小、显式、容易推理”的目标有距离。上面几条是规模的来源之一：每多一处独立判断和一份镜像，就多一组需要对齐的校验。

## 已有的方向

方案建立在这些已接受的结论之上：

| 来源 | 结论 | 这里怎么用 |
| --- | --- | --- |
| 统一执行协议 | 每个问题一个权威；候选是临时的纯值；准入和结算各是一个事务 | 准入路径不变，结果的投递仍经过 `AdmitExecution` |
| 统一执行协议 | 新增一个准入权威必须在同一变更里替换掉一个旧的 | 方案不新增持久化的候选、预留或镜像表 |
| 统一执行协议 | 普通的类型化冲突不得造成无界重试 | 扩展到结算账本：等待也必须有界或有触发条件 |
| [恢复预算](../rfcs/task-result-recovery-budget.md)，#4101 修订 | 无法推进的义务在内存里退避；相关的已提交变化可以让它提前合格 | 第 2 节把“相关变化”定义成封闭的触发集合 |
| [结果内容与呈现](../rfcs/task-result-content-and-presentation.md)，#4101 修订 | owner 暂时等待时回复留在原队列项上；历史上被丢弃的回复停止自动重检，仍可由精确 waiter 认领 | 判定表按此填写 |

另外采用四条前提，它们是对常驻状态层的工作结论：

- 读不取写所有权，直接读已发布的根。
- 读准备不进入写事务。
- 类型化的并发冲突是可重试的，不是致命错误。
- 已加载 agent 的当前状态在启动时完整加载，之后只由已提交的增量维护。

需要补充的一点：最后一条和按请求形状发布的 coverage 不能共存。只要 coverage 里还有形状字段，增量就无法保持它“相等”，这正是 #4095 窄路径回退的原因。

## 目标与非目标

目标：

- **完整**：任一未结算结果在任一时刻有且只有一个确定的下一步，每个状态都有出口。
- **无进展则无写入**：等待中的结果在条件不变时不产生任何数据库写。
- **空闲零成本**：没有新事件、没有到期期限的 agent，loop 不读库、不写库。
- **形状无关**：常驻视图不记录调用方的请求形状，也不记录时间。
- **交互优先**：operator 的写不排在后台恢复写后面。

非目标：

- 不引入多通道并发执行，不替换 provider turn loop。
- 不改变信任、来源、权限的判定，不放松精确 wait 的安全规则。
- 不改变“先持久化再投递给模型”和提交后才发布的顺序。
- 不新增持久化的生命周期镜像。
- 不处理 Work、Input、Scheduling 域的同类问题，先在 Task 域验证做法。

## 方案

### 1. 一个决定函数

引入一个纯函数，输入是一条未结算结果和它相关的事实，输出是下一步：

```rust
enum Step {
    /// 现在可以投递。`via` 说明经由哪个已有的准入来源。
    Deliver { via: Admission },
    /// 现在不能投递。`until` 列出能改变这个结论的事件，不能为空。
    Hold { reason: HoldReason, until: Vec<Trigger> },
    /// 不会再投递，用已有的处置值结算。
    Settle { disposition: Disposition },
    /// 运行时无法自行推进，停止自动处理并让 operator 可见。
    Park { diagnostic: Diagnostic },
}

fn next_step(result: &ResultFacts, owner: &OwnerFacts, lane: &LaneFacts, now: Time) -> Step
```

约束：

- **穷举**：输入是有限的枚举组合，函数体是对它们的穷举匹配，新增一个状态而不处理会编译失败。
- **`Hold` 必须可解除**：`until` 里的每个触发条件来自一个封闭的枚举，并且有测试证明每一种都能由某个已有的状态转换产生。
- **不写库**：函数只返回结论，由调用方用已有的转换去应用。准入仍然只有 `AdmitExecution` 一条路径。
- **时间是参数**：`now` 由调用方传入，不存进任何快照。

所有需要判断结果去向的地方都调用它：恢复扫描、空闲时的结果准入、`WaitFor` 的快路径、调度认领里处理 TaskResult 和回复的分支。今天的“投递通道”变成 `Deliver.via` 的取值，而不是各自独立的代码路径。

下表是这个函数要实现的判定，也是这篇最需要讨论的部分。“现在”一列是基线上恢复扫描的行为。多数行的结论和现在一致，区别在于它们由一个函数给出，等待的行各自写明了由什么解除。

| 结果与 owner 的状态 | 现在 | 建议 |
| --- | --- | --- |
| 结果依赖关系无效 | 结算 `invalid_or_stale` | 不变 |
| 义务无效或过期，可证明 | 收敛结算 | `Settle` |
| 义务无效或过期，证据不足 | 内存退避 | `Park`，不再自动重试 |
| owner WorkItem 已关闭或不存在 | 结算 `owner_closed` / `owner_missing` | 不变 |
| admission 正在进行 | 内存退避 | `Hold`，直到该 attempt 结算 |
| 已被其他 waiter 认领 | 内存退避，该 wait 变化时唤醒 | `Hold`，直到该 wait 解决或取消 |
| owner 有未解决的 wait | 内存退避，相关变化时唤醒 | `Hold`，直到该 wait 解决或取消 |
| owner 不可运行 | 内存退避，相关变化时唤醒 | `Hold`，直到该 WorkItem 状态变化 |
| 执行通道被占用 | 内存退避，相关变化时唤醒 | `Hold`，直到通道空闲 |
| 回复已被别处消费 | 结算 `reply_consumed_elsewhere` | 不变 |
| 回复队列项已丢弃，有精确 waiter | 由该 waiter 认领 | 不变 |
| 回复队列项已丢弃，没有 waiter | 标记 `awaiting_exact_waiter`，停止自动重检 | `Hold`，直到精确 waiter 注册 |
| 回复队列项仍在排队 | 内存退避；owner 可运行后由调度认领原消息 | `Hold`，直到该队列项到达终态 |
| 生命周期 owner，锚点 turn 已终结且无其他入口 | 结算 `invalid_or_stale` | 不变 |
| 可投递，同一 owner 已有恢复唤醒在排队 | 内存退避 | `Hold`，直到该唤醒到达终态 |
| 可投递，预算内 | 持久化延期后入队恢复唤醒 | `Deliver` |
| 可投递，退避期内 | 延期 | `Hold`，直到退避期限 |
| 预算用尽 | 暂停并发布诊断 | `Park` |

### 2. 事件驱动的等待

`Hold` 的触发条件是一个封闭集合：

| 触发条件 | 由什么产生 |
| --- | --- |
| wait 解决或取消 | wait 的状态转换 |
| WorkItem 执行状态变化 | 结算、控制命令 |
| attempt 结算，通道空闲 | 终态结算 |
| 精确 waiter 注册 | `WaitFor` |
| 队列项到达终态 | 认领、丢弃、隔离 |
| 期限到达 | 仅用于恢复预算的退避 |
| operator rearm | 控制命令 |

#4101 已经有了这个机制的雏形：提交后用本次转换的 effects 去唤醒内存里的探测记录。区别在于：

- **触发条件由 `Hold` 声明，而不是由唤醒逻辑按原因字符串推断。** 判定和唤醒共用一份定义，新增一种等待时不会漏掉对应的唤醒。
- **非期限类的等待没有定时器。** 现在的内存退避仍然是带退避的轮询，事件只是让它提前。改为纯事件驱动后，期限只保留给恢复预算的退避。
- **内存索引是唯一的等待状态。** 从触发条件到结果的索引在启动时对账本只读地跑一遍 `next_step` 重建。只在结论的种类或原因变化时写库，用于重启恢复和诊断。
- **保留一个低频的只读核对**（例如每 10 分钟）：从库里重算结论并与内存比较。一致则什么都不做；不一致说明漏了事件，记录计数并重新决定。它是漏事件的兜底，也是发现缺陷的探针。

长期等待靠年龄发现：一条结果在 `Hold` 里超过阈值（例如 24 小时）就发布一次诊断。是否到期后自动 `Park`，见讨论问题 2。

### 3. loop 变成“事件 → 决定 → 应用”

现在的每轮循环依次做恢复扫描、agent wait 重检、调度轮询，每一步各自准备所需的域（[runtime.rs](../../src/runtime.rs#L6909-L6916)）。建议的形态：

```text
loop {
    等待：提交通知（带本次变化的事实集合）| 最早的期限 | 关闭
    view  = 已发布的根                 // 不读库
    steps = decide(view, changed, now) // 纯函数
    apply(steps)                       // 每个是一条窄命令；准入仍是 AdmitExecution
}
```

- 恢复扫描和 wait 重检不再是独立的阶段。它们的输入并入 `decide`，输出是 `Step`。
- `decide` 分两部分：对受影响的结果调用 `next_step`，以及现有的候选选择。候选选择的规则不变。
- 调度读使用已发布的根，时间作为参数传入。“带恢复来源的调度读每次都重建 Task 域”的问题随之消失。
- 没有变化的事实、也没有到期期限时，循环体不执行。

这一步不改变任何准入规则，改变的是谁在什么时候触发判断。

### 4. Task 域的常驻视图

在“完整加载加增量维护”的前提上加三条：

- **coverage 只包含活动集合**：活动 Task、未结算结果及其关联的 Task。这个集合按定义是完整的，由每次 Task 域写入产生的增量维护。#4095 的窄 `Defer` 是增量的样板。
- **历史按需读取**：terminal 窗口、查询选择、按 key 的查找，通过有界的只读查询获取，按 key 缓存，可以合并。它们不属于 coverage，也不参与相等比较。
- **coverage 不含形状和时间**：去掉 `required_keys`、terminal 窗口大小、查询选择和 `recovery_at`。需要时间的判断把 `now` 作为参数。

重建只在两种情况发生：启动，以及增量的基础 revision 对不上。重建在只读连接上完成，写事务只做短校验和必要的持久化。写入默认是窄的：声明前置条件，产生增量。现有的全量快照路径保留为恢复手段。

terminal 窗口移出 coverage 是否可行，取决于谁在依赖它，见讨论问题 3。

### 5. 写入车道

- writer 队列分交互和后台两级，交互写优先。
- 后台结算可以合并：同一个 agent 的多条 `Settle` 在一个事务里提交。
- 纯读移出 writer，#4087 已在推进。

## 迁移步骤

每一步可以独立合并和回滚，前一步不依赖后一步。

| 步骤 | 内容 | 状态 | 验收 |
| --- | --- | --- | --- |
| 0 | 计数：窄路径回退原因、Task 准备的调用方和未命中原因。把判定表写成针对现有行为的特征测试 | #4101 加了恢复和窄路径归因；Task 准备按调用方的归因和特征测试未做 | 线上能回答“哪个调用方、为什么重建” |
| 1 | 修复用条件：带恢复来源的调度读在事实未变时复用已发布快照 | 未做 | 状态不变时连续两次空闲调度读，第二次 Task 域加载为零 |
| 2 | 无法推进的结果不写库，两条死路有出口 | #4101 已完成，形式是内存退避和收敛操作 | 60 条不可投递的结果，writer 每分钟持锁低于 1 秒 |
| 3 | 引入 `next_step`，恢复扫描改为调用它；触发条件改为封闭集合，加只读核对，去掉非期限类的定时器 | 未做 | 空闲 agent 的 loop 在 10 分钟内零读写；核对不一致计数为零 |
| 4 | 其余通道改为调用 `next_step`，删除重复的判定函数 | 未做 | 判定逻辑只剩一处；特征测试全部通过 |
| 5 | Task 域 coverage 去形状化，增量维护 | #4095 完成了 `Defer` 一种写入 | 写入不触发全量重建；增量结果与全量重算逐字段相等 |
| 6 | loop 合并阶段，writer 分级 | 未做 | 饱和负载下 `POST /prompt` 的 writer 排队 p95 低于 100 毫秒 |

步骤 0–1 改动小，直接针对线上剩余的重建。步骤 3–4 是结构上的核心。步骤 5–6 范围最大，应和常驻状态层的后续工作合并排期。

## 风险

- **漏事件导致结果卡住。** 事件驱动把正确性押在“每个触发条件都有人发出”上。缓解是启动时重算、低频只读核对，以及“每种触发都能被产生”的测试。
- **增量维护的正确性。** 用 #4095 已有的方法验证：增量安装后的常驻域与全量重算逐字段相等。可以在调试构建里保留影子重算。
- **改动落在校验最密的路径上。** 步骤 4 会删除多个各自有测试的判定函数。先有特征测试，再替换，每次只迁移一个调用方。
- **与进行中的工作冲突。** #4074 的后续切片会碰同一批文件，需要先对齐顺序。

## 需要讨论的问题

1. **投递规则能否收敛成两句话？** 一个结果只有在两种情况下可以启动一次 attempt：它有精确 wait，或它的 owner 可运行。而任何时候 owner 的 attempt 因为任何原因启动，都把该 owner 所有可投递的结果一并附上，沿用现有的每批 8 条上限。统一执行协议写明不得把准入权授予没有 wait 的或过期的结果，这条规则没有违反它，因为这些结果不启动 attempt，只是搭车。如果成立，多数通道会合并成一条。

2. **长期等待要不要自动 `Park`？** 例如 owner 在等 operator 且已经三周。自动 `Park` 让状态有界，但可能把合法的长等待变成需要人工处理的事项。另一种做法是只发诊断，不改变状态。

3. **terminal 窗口能否移出 coverage？** 需要确认谁在依赖常驻的最近 128 个 terminal Task：上下文渲染、State 投影，还是只有按需查询。

4. **热路径上的资源记账是否确定移除？** `next_step` 作为纯函数的前提是读已发布的根不需要登记预算。

5. **步骤 1 是否先作为独立的热修复合并？** 它不依赖判定表，但会改动调度读对恢复来源的处理，需要确认 `recovery_at` 是否参与到期判断。

6. **契约放在哪？** 建议把“结果处理”作为统一执行协议的一节，而不是新开 RFC。那份协议要求新增权威必须替换旧权威，结果处理正是要从“第二个调度阶段”收回到这份协议里。

## 局限

- “约 12 处判定函数”“约 12 个子系统”“约 30 个拒绝原因”来自一次代码结构梳理，没有逐一核对，可能有出入。规模数字取自 `464c5e498`。
- 判定表的“现在”一列根据恢复扫描的代码整理，其他通道的行为没有逐行对照。
- 事故数据取自 `7164c2f08` 和 `464c5e498`。#4101 的线上效果没有验证。
- 每个循环周期三次重建的机制在采样的三个 agent 里观察到了两个，它占全部重建的比例没有量化。
- 方案只在 Task 域论证过。Work、Input、Scheduling 域是否有同样的形状问题没有检查。
