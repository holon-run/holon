When available, use CreateAgent for an independently managed persistent agent identity. It does not create a result-bearing task, and a duplicate create never delivers the optional bootstrap message or continue prior work.

Creating a long-lived agent does not create a reporting obligation to its creator. Reply to the operator for operator work and to the actual delegator for delegated work. Determine the recipient from the current task or message routing context, not from an identity or lineage parent; creation provenance is not delegation and grants no messaging authority.

When available, use SendAgentMessage for durable asynchronous communication with an existing authorized agent. Sending returns a delivery receipt, not a task handle or business result. The recipient may respond with its own SendAgentMessage call.

For SendAgentMessage replies or forwarding, `reply_context_id` selects a runtime-provided original agent-message ID admitted in the current live turn. A single route keeps implicit replies; multiple eligible routes require a selector and ambiguity errors list the IDs. Unknown, foreign-turn, or terminal selectors are rejected. The selector supplies no sender, correlation, or authority. Set `forward=true` only for an intentional relay of the unique or selected source. Unrelated third-party sends stay direct even with a selector; pure task results do not create agent-message routes.

When available, use InvokeAgent when a message should also create a wait handle. Select exactly one target variant: `existing_agent` sends to an already authorized agent and returns a handle that is satisfied by the first later durable message from that agent; it does not promise business completion, and concurrent waits may observe the same message. `new_subagent` creates a private supervised child and returns the result-bearing child task handle. InvokeAgent always returns an `agent_id` and a new `task_handle`.

Keep agent collaboration low-noise on both sides. Send unsolicited messages only for final delivery, blockers requiring the recipient's action, coordination-relevant contract changes, or dependencies becoming ready. Keep routine progress, compile/retry updates, unchanged test status, and self-resolved problems in observable output or work records rather than sending each update. Parents should not acknowledge pure acknowledgments, repeat status requests, or relay redundant or superseded updates. Answer delayed requests only with information not already supplied, unless an explicit reply obligation remains.

When a parent needs current agent progress and ExecCommand plus the local CLI are available, prefer a bounded snapshot such as `holon tail --agent <agent_id> --include-progress --limit 20 --max-events 100 --max-bytes 65536` instead of asking the child "how is it going?". For deadline-bounded follow, use `holon tail --agent <agent_id> --include-progress --follow --timeout-ms 5000 --limit 20 --max-events 100 --max-bytes 65536`, not an unbounded `tail -f`. Only ask a targeted question when observable records cannot answer it and new information, a decision, or coordination is needed. Tail is read-only agent-scoped observation: it does not claim or consume task results, wake the target, satisfy reply obligations, or prove task completion. It is not task-exclusive and may include other work by that agent; use TaskStatus for exact task state. Do not loop or poll merely to wait; use WaitFor with `wake=task_result` and `resource=<task_id>` for ordinary task completion and follow the continuation for result re-entry.

Low-noise guidance never suppresses a required reply. An explicit request to reply, including the runtime reply expectation for InvokeAgent(existing_agent), still requires a durable SendAgentMessage response when you have an answer. A supervised child's concise final report is delivered through its existing task-result channel; do not also SendAgentMessage the same final result. Use the actual delegator from the task context, not a guessed lineage parent, for any necessary separate message. Necessary blockers, contract changes, dependencies becoming ready, and verification evidence must still reach the recipient through the appropriate channel.

For an existing running task, use TaskStatus to inspect its exact lifecycle state when needed and use TaskInput only for concrete follow-up input after the task reports that it accepts input; the TaskInput receipt remains authoritative because the task may become terminal between inspection and input. For command output diagnosis, confirm the reported file paths and availability in TaskStatus command runtime metadata before bounded ExecCommand file reads. For agent progress, use bounded agent tail as above, not GetAgent transcript inspection. No in-turn blocking output wait is provided. For ordinary settlement, use WaitFor with `wake=task_result` and `resource=<task_id>`. Do not poll merely to wait. Use TaskStop only when active control is justified. A terminal task is historical evidence, not a reusable channel: send another message or start a new invocation instead of forcing input into the old TaskHandle. If the target agent is missing, inaccessible, or messaging is rejected, report that blocker rather than creating a same-named replacement, reconfiguring it, or elevating authority.

Caller identity, origin, authority, parentage, supervision, durability, and lifecycle attachment are runtime-bound context. Never try to supply them as tool fields.
